The generated contract carries `info.x-darpan-contract-version`, decoupled from the product release version. The policy is additive-only: new methods, new optional parameters, and new response fields ship without a bump; breaking changes require a conscious one. See [Contract versioning](/api-reference/json-rpc#contract-versioning).

Releases 1.3.0, 1.4.0, 1.5.1, 2.1.3 to 2.1.12, 3.0.2, 3.0.3, 3.2.1, 3.3.1, 3.3.2, 3.4.1, 3.4.2, 3.4.4, 3.4.5, 3.4.6, 3.4.7, 3.4.8, 3.4.10, 3.4.11, 3.4.14, 3.4.15, 3.4.16, 3.5.1, 3.5.2, 3.5.3, 3.5.4, 3.5.5, 3.5.6 and 3.5.7 added or removed no methods. <Note>
Operator-only methods (`admin.*`) are listed in the [service catalog](/api-reference/service-catalog#administration) but are not part of the public API. They serve the operator admin application and require a super-admin caller, so integrations should not depend on them. The counts below mention them only so the totals add up.
</Note>

## Contract version 6

Darpan 3.5.0 to 3.5.8. Current.

### Darpan 3.5.8

Adds `facade.AuditFacadeServices.remove#AuditCheck` (243 public methods); additive, so the contract stays at 6. It takes `audit` and `check` and answers `removedCheck` `{id, automationId, automationStopped}`; it is refused while the check has open findings. 3.5.8 is deployed in place of 3.5.7.

### Darpan 3.5.7

No method, parameter or field added or removed (242); the contract stays at 6. Chat posts change shape only (cards with `fallbackText`); no API answer changes.

### Darpan 3.5.6

No method, parameter or field added or removed (242); the contract stays at 6. `get#GeneratedOutputDifferences` also names the result's run in `metadata.reconciliationRunResultId` (a free-form map).

### Darpan 3.5.5

No method, parameter or field added or removed (242); the contract stays at 6.

### Darpan 3.5.4

No method, parameter or field added or removed (242); the contract stays at 6. 3.5.2 and 3.5.3 were cut and never deployed; 3.5.4 carries them.

### Darpan 3.5.3

No facade method, parameter or field added or removed (242); the contract stays at 6. `netsuite-darpan`'s `extract#NetSuiteOrders` reads by change from an audit's start (`changedSince`), and `darpan-hotwax` adds the internal `reconciliation.HotWaxOmsExtractionServices.read#HotWaxOmsChangedOrderIds` (not remote).

### Darpan 3.5.2

No method, parameter or field added or removed (242); the contract stays at 6. The acknowledgement-note migration (`ACK_NOTE_NULLABLE`) now runs outside its caller's transaction.

### Darpan 3.5.1

No method added or removed (242). `save#SyncPair` and `save#PeakPeriodSync` accept a pulse on a check whose upstream side is Shopify orders as well as HotWax orders; any other upstream is refused with "A pulse needs HotWax or Shopify orders as the upstream side." (was "A pulse needs HotWax as the upstream side.").

### Darpan 3.5.0

Four methods added and five removed (242), and one parameter removed, so the contract moves to 6:

- Added: `facade.IdIndexFacadeServices.search#RecordIds` (an id, any spelling, found in the tenant's ID index and followed through the values its records share, up to 4 hops and 200 records; identifiers only), `get#IdIndexStatus` (how current the index is per kept copy), `save#TenantIdIndexField` and `delete#TenantIdIndexField` (a tenant's own ID fields; a path that looks like a customer detail is refused).
- Removed: `facade.LookupFacadeServices.get#LookupCatalog`, `save#TenantLookupRead`, `delete#TenantLookupRead`, `save#TenantLookupLink`, `delete#TenantLookupLink`. The order lookup no longer reads connected systems, so it has no reads or links to manage.
- Changed: `lookup#Order` loses `all` and answers from the ID index: `{value, records, findings, notSeen, capped, cappedReason}`. It calls no connected system.

## Contract version 5

Darpan 3.4.0 to 3.4.17.

### Darpan 3.4.17

No method added or removed (243); one optional parameter added, so the contract stays at 5:

- `facade.AuditFacadeServices.run#Audit` takes `checks`: check codes to play; only their automations run. None plays every check.

### Darpan 3.4.16

No method added or removed (243), and no parameter added, so the contract stays at 5:

- `facade.AuditFacadeServices.acknowledge#AuditFinding` and `update#AuditFindingAcknowledgement`: `note` is optional. A blank note acknowledges the row with no note (an acknowledgement's `note` is then null), and a blank change clears it. Over 4,000 characters is still refused. `send#AuditFindingFeedback` still needs a note.

### Darpan 3.4.13

Six methods added (243), so the contract stays at 5:

- `facade.LookupFacadeServices.lookup#Order`: follow one order id through every connected system, with its open findings; customer details only with `all`.
- `facade.LookupFacadeServices.get#LookupCatalog`, `save#TenantLookupRead`, `delete#TenantLookupRead`, `save#TenantLookupLink`, `delete#TenantLookupLink`: the reads and links an order lookup follows, and a tenant's own overrides and additions. A read's template must be read-only for its system.
- `get#AuditRecheckProgress` also reads `since` as epoch milliseconds or an ISO instant, as a page sends back `verify#AuditFindings`' `checkedSince`.

### Darpan 3.4.12

Four methods added (237), one optional parameter and one response field added, so the contract stays at 5:

- `facade.AgentChangeFacadeServices.propose#AuditChange`: a person proposes an audit change through their own AI and the CLI, with no agent conversation. Their words and the finding they name vouch for nothing but that finding and the config; every other value comes back in `unconfirmedIds`. Needs edit access on the active tenant.
- `facade.AgentChangeFacadeServices.get#AuditChangeProposal` and `list#AuditChangeProposals`: one proposal as a person reviews it (before and after, the backtest, unconfirmed values, `planHash`), and the active tenant's proposals, newest first, at most 100, optionally by status (`OPEN` for DRAFT, PLANNED, STALE and INVALID).
- `facade.AgentReadFacadeServices.find#AuditFindingLookalikes` is now callable remotely: findings of the same check that share a finding's cause, and controls with a different one.
- `apply#AuditChange` takes optional `confirmedIds`. A person's proposal that is `BLOCKED` applies only when they equal its whole `unconfirmedIds` list.
- `get#AuditReport`: each statement's check carries `systems`, the systems it compares (`OMS`, `NetSuite`, `Shopify`), named from the check's label, else its statement, else its automation's sources, whether or not it ran that morning. A finding's records include the record its check's conclusion lookup read in another system.

### Darpan 3.4.11

No method added or removed (233), and no parameter or field changed, so the contract stays at 5:

- A CLI sign-in reaches every tenant method the person's role allows; each method checks the role itself. Connection credentials, sign-in, installs, `admin.*` and the audit agent's chat stay out of its reach.
- `facade.SourceEndpointFacadeServices.store#SourceConfigEndpointAccess` needs edit access on the active tenant; a view-only member is refused with "Your active tenant only has view access for connections."

### Darpan 3.4.10

No method added or removed (233); two optional parameters added, so the contract stays at 5:

- `facade.ReconciliationFacadeServices.save#RuleSetRun` takes `file1ExtractOptions` and `file2ExtractOptions`, maps of a side's read options, as `create#RuleSetRun` does. Omitted keeps the side's stored options, sent replaces them, and an empty map clears them. A name the side's connector does not declare (`extractOptionsJson`) is refused, in words, before anything is written.

### Darpan 3.4.9

Seven methods added (226 to 233), and parameters and fields added only, so the contract stays at 5. Nothing was removed.

- `facade.AuditFacadeServices.acknowledge#AuditFinding`, `update#AuditFindingAcknowledgement` and `delete#AuditFindingAcknowledgement` acknowledge, change and reopen the report row holding one open finding: a required note (at most 4,000 characters) and an optional remind day (`audit.acknowledge.remindDays`, default 5). A finding stays open or fixed; an acknowledgement takes its row out of `open` only. They need access to the tenant, not edit access, and are not on the CLI allowlist.
- `facade.AuditFacadeServices.send#AuditFindingFeedback` saves a note to Darpan about one finding, posts it to Darpan's feedback chat space and emails the sender a thank-you. `get#AuditFindingFeedback` lists the tenant's notes on the finding's statement and cause within `audit.feedback.shownDays` (default 14). Send is not on the CLI allowlist; the list is.
- `facade.AuditFacadeServices.verify#AuditFindings` re-checks every open finding of an audit's period, or of one statement, with one run per automation (more past 1,000 orders), and writes no check run. `get#AuditRecheckProgress` counts the findings checked since its `checkedSince` and how many closed. `verify#AuditFindings` needs run access. Neither is on the CLI allowlist; `verify#AuditFinding`, for one finding, stays on it.
- `get#AuditReport`: the counts carry `acknowledged`, and `open` leaves out the rows acknowledged today, on the latest morning only. Each open row carries `acknowledgement` (`{note, by, at, remindOn, reminded}` or null), and `report.acknowledgeRemindDays` is the setting. `get#AuditFindingsByOrder` now reads `state` (`open`, `acknowledged`, or blank for every open row; any other value is an error) and each row carries `acknowledgement`.
- `get#AuditFinding`: `acknowledgement` and `feedback.recentCount`. History can carry a person's events, `acknowledged`, `acknowledgementChanged` and `acknowledgementReopened`, which never decide a finding's state.
- Operator-only: `admin.FeedbackAdminServices.get#FeedbackList` and `reply#Feedback` list the feedback across tenants and answer one by email. Both are kept off the `darpan` CLI allowlist; the `darpan-admin feedback` command calls them as a super admin.

### Darpan 3.4.8

No method added or removed (226), and no parameter or field changed, so the contract stays at 5. The order lines of 3.4.7 are now turned on by connector read options, which are data: `withLineItems` on the `SHOPIFY` connector and `withOrderItems` on `OMS_GQL` (darpan-hotwax 1.3.4). They appear in a side's `extractOptions` and are saved in its extract parameters like any other option.

### Darpan 3.4.7

No method added or removed (226); a field added only, so the contract stays at 5:

- `facade.AuditFacadeServices.get#AuditFinding` and the findings of `get#AuditReport`: an order record carries `lines` when its read gave them, each `{id, sku, name, quantity, status}`. A Shopify orders read gives them with `withLineItems` (shopify-darpan 0.11.2), a HotWax orders read when it asks `orderItems` (darpan-hotwax 1.3.3). `id` is the Shopify line id on both systems, so a line and its HotWax item pair. A Shopify line's `status` is `Removed`, `Fulfilled`, `Unfulfilled` or "1 of 3 unfulfilled"; a HotWax item's is its status in words. Without either option, no record carries `lines`.
- `facade.ReconciliationFacadeServices.run#SavedRunDiff`: a run that fails, or whose rules do not fully evaluate, no longer sends its error to notify-me subscribers. They get "*name* did not finish. Darpan has been alerted and is working on a fix." No parameter or return field changed.
- Operator-only: `admin.SettingAdminServices.update#Setting` checks `audit.unexplained.email.to` as a list of email addresses.

### Darpan 3.4.6

No method added or removed (226); fields added only, so the contract stays at 5:

- `facade.AuditFacadeServices.get#AuditReport` and `get#AuditFinding`: each record carries `paymentStatus` when its read gave one, in its system's words: a Shopify financial status, a HotWax order's payment statuses (each once, or `No payment`), a HotWax return's `Refunded` or `Not refunded`, a NetSuite order's or line's deposit statuses. A Shopify record's `status` is now its fulfillment status alone; its financial status was folded into `status` before. A Shopify return's `returnDate` is its `closedAt` when it has no other.
- `facade.AuditFacadeServices.run#Audit` and the morning run: the re-check also reads, on a side whose extractor takes `changedSince` (HotWax orders, darpan-hotwax 1.3.2), the period's records that changed since the recent read started. A check whose changed read fails is partial, with "Records changed since the last read were not re-read:" and the reason.
- `get#AuditReport`: a check whose run read no records on one side, or kept none, while the other side read some, is `notRun` with the side's reason, and closes nothing.
- Operator-only: `admin.SettingAdminServices` settings can be `STRING`, and a `secret` one is masked in every answer and audit row. `update#Setting` checks `errors.chat.webhookUrl` and `errors.email.to`.

### Darpan 3.4.5

No method added or removed (226), and no parameter or field changed, so the contract stays at 5:

- `facade.AuditFacadeServices.get#AuditSettings` lists, under each statement, only the `reasons` its checks can reach. A check reaches the conclusions of the rows it reports: its link's row kinds map to the conclusion buckets the engine uses, and a blank list reaches them all. Statements whose checks share one saved run no longer each list the run's whole tree. `closes` and `closesOn` count the reached checks only, so `save#AuditSettings` refuses a level only on a reason that closes on every check that reaches it. A level already saved on a reason the statement no longer reaches is still listed, with `checks` 0, so it can be cleared. Two rule checks on one run still share their rule reasons.

### Darpan 3.4.4

No method added or removed (226); parameters and fields added only, so the contract stays at 5:

- `facade.AuditFacadeServices.get#AuditSettings` returns each statement's `priority` and its `reasons` (`conclusion`, `label`, `priority`, `closes`, `closesOn`, `checks`). `save#AuditSettings` takes a statement's `priority` and a new `reasons` list of `{statement, conclusion, priority}`; it refuses a level on a reason that closes on every check.
- `get#AuditReport`: each finding carries `priority`, `prioritySource`, `priorityReason` and `priorityLine`, and the counts carry `byPriority`. `get#AuditFindingsByOrder` takes `priority`.
- `get#AuditReport` and `get#AuditCheckExtracts`: a blank `date` is now the last morning that was due (yesterday until today's scheduled run), not always today. `retry#AuditCheck` keeps today.
- `get#AuditProgress` adds `asOf`, per step `movedDate` and `expectedRecords`, and per running run `limits`.
- `facade.AgentTurnFacadeServices.send#AgentTurn` takes `statement`.

### Darpan 3.4.3

One method added (225 to 226), additive, so the contract stays at 5:

- `facade.TenantScriptFacadeServices.save#TenantQueryPins` saves the caller's pinned queries for the active tenant (`pinnedQueryIds`, in order; unknown or other-tenant ids are dropped). Not on the CLI allowlist.
- `facade.TenantScriptFacadeServices.list#TenantQueries` returns `pinnedQueryIds`, the caller's pins for the tenant in pin order.

### Darpan 3.4.2

No method, parameter or field changed. `facade.ReconciliationFacadeServices.run#AutomationNow` (and every other call that starts a run under a requested tenant) now reads both sides in that tenant: a side read in parallel used the caller's saved tenant. The exchange presence step no longer records `deferredLookupCount`.

### Darpan 3.4.1

An automation keeps its own filters again (3.4.0 had it read its run's live):

- `facade.ReconciliationFacadeServices.save#Automation` takes `sources[].excludeFilters` again; a source that leaves it out keeps the filters it has. `get#Automation` sources carry `excludeFilters`. `sync#Automation` copies the run's filters, and `syncStatus.changedFields` names `FILE_1.excludeFilters` or `FILE_2.excludeFilters` when they differ.
- `facade.AgentChangeFacadeServices.apply#AuditChange` syncs each automation of the run after an exclusion, and refuses with `AUTOMATION_DRIFT` when one already differs from its run, filters included.
- `facade.TenantConfigFacadeServices.preview#TenantConfigRestore` and `admin.TransferAdminServices.import#ConfigBundle` no longer block with `AUTOMATION_FILTERS_DIFFER`. A version or bundle carries each automation's filters; one saved on 3.4.0 carries none, and each automation takes its run's.

### Darpan 3.4.0

The generated contract moves to version 5 because methods are removed: the 8 tenant script methods (`facade.TenantScriptFacadeServices` list, save, delete and run for scripts and their deployments) are gone; queries replace scripts. 25 public methods are added (208 to 225). One request field is dropped and is ignored when sent (see below). One response field of an operator-only method is renamed (see below).

Peak periods:

- `facade.PeakPeriodFacadeServices.list#PeakPeriods`, `get#PeakPeriod`, `save#PeakPeriod`, `delete#PeakPeriod`: the active tenant's busy date ranges, with peak hours, a HotWax read share and serial NetSuite reads.
- `facade.PeakPeriodFacadeServices.save#PeakPeriodRunTime`, `delete#PeakPeriodRunTime`: start an automation or audit at a set time inside a period.
- `facade.PeakPeriodFacadeServices.save#PeakPeriodSync`, `delete#PeakPeriodSync`: a sync pair's allowance and pulse for one period.

Sync pulse:

- `facade.SyncPulseFacadeServices.list#SyncPairs`, `get#SyncPair`, `save#SyncPair`, `delete#SyncPair`: a light watch on a daily check, sampling every few minutes for orders the other system has not received.
- `facade.SyncPulseFacadeServices.get#RunPulseFlags`: the records of a daily-check run the pulse had already flagged.

- `facade.SyncPulseFacadeServices.get#SyncPair`: `syncPair.periodThruDate`, the overriding peak period's last day.

Audit reads:

- `facade.AuditFacadeServices.get#AuditReadReport`: what one play of an audit read, grouped by endpoint and connection, with flags where a read cost more than it needed.

Queries (DAR-BE-334), on the moqui-jexl component:

- `facade.TenantScriptFacadeServices.list#TenantQueries`, `save#TenantQuery`, `delete#TenantQuery`, `run#TenantQuery`: the active tenant's queries, a read over what its audits keep plus a JEXL script.
- `facade.TenantScriptFacadeServices.list#TenantQuerySchedules`, `save#TenantQuerySchedule`, `delete#TenantQuerySchedule`, `run#TenantQuerySchedule`: daily schedules that email the answer and post its summary to a chat space. Saving, deleting and running one needs tenant admin; sending by hand, its owner.
- `facade.TenantScriptFacadeServices.get#TenantQueryCatalog` and `create#TenantQueryProposal`: what a query may read, and a proposed query checked against it and run first.
- `facade.AgentTurnFacadeServices.send#AgentQueryTurn`: the queries page's agent (`darpan-agent`), with the page's optional `readSpecJson` and `scriptBody`.
- Removed: `facade.TenantScriptFacadeServices.list#TenantScripts`, `save#TenantScript`, `delete#TenantScript`, `run#TenantScript`, `list#TenantScriptDeployments`, `save#TenantScriptDeployment`, `delete#TenantScriptDeployment` and `run#TenantScriptDeployment`. A client that calls one gets method not found. The 3.4.0 migration `TENANT_SCRIPTS_TO_QUERIES` copies each script into a query and each deployment into a schedule, switched off.
- `facade.SettingsFacadeServices.get#NotificationRoutes` lists a query schedule's chat delivery as the `SCRIPT` route (its `sourceId` is the schedule's id). `set#NotificationRoute` for `SCRIPT` moves that delivery, needs tenant admin, and still refuses no space.

Changed behaviour of existing methods:

- `facade.ReconciliationFacadeServices.list#Automations` adds `effectiveNextStart`, `peakPeriodName` and `peakHoursUntil` to each automation, and `facade.AuditFacadeServices.get#AuditSettings` and `save#AuditSettings` add `peakHoursUntil` to `settings`.
- `facade.AuthFacadeServices.begin#PasskeyRegistration` may leave out the code or passkey assertion within 5 minutes of a sign-in that completed two-factor, on the session it made.
- `facade.RunConclusionFacadeServices.save#RunConclusions` accepts the condition operator `LT`, less than one number.
- A CLI session may now call `save#RunConclusions`, `create#RunConclusionCode` and `sync#Automation`, the new peak period and sync pulse reads, and the ten query methods in place of the script ones. The new peak period and sync pulse saves and deletes, and `send#AgentQueryTurn`, are refused to it.
- An automation keeps no filters of its own: every run of it reads its compare scope's filters. `facade.ReconciliationFacadeServices.save#Automation` drops `sources[].excludeFilters`; a client that still sends it is not refused, and nothing is written for it. `get#Automation` sources no longer carry `excludeFilters`. `sync#Automation` no longer copies filters, and `syncStatus.changedFields` never names one.
- `facade.AgentChangeFacadeServices.apply#AuditChange` no longer refuses an exclusion with `AUTOMATION_DRIFT`. The exclusion writes the run's filter only.
- `facade.TenantConfigFacadeServices.preview#TenantConfigRestore` blocks a version made before 3.4.0 with `AUTOMATION_FILTERS_DIFFER` when an automation's own filters in it differ from its run's. Equal ones are dropped.

Operator-only `admin.*` changes, outside the public API:

- `admin.MembershipAdminServices.add#TenantMember` returns `welcomeSent` and `welcomeWithPassword` in place of `welcomeQueued`, and waits for the mail server. `send#TenantWelcome` waits too, and returns `withPassword`. The welcome email carries the temporary password while one is kept.
- `admin.RetentionAdminServices.update#RetentionPeriods` and `dryRun#Retention` take the table key `SYNC_PULSE_SAMPLE`.
- `admin.AgentConfigAdminServices.update#AgentRoleModel` takes the role `AUDIT_READ_REVIEW`.
- `admin.TransferAdminServices.import#ConfigBundle` blocks an older bundle with `AUTOMATION_FILTERS_DIFFER` on the same rule. A 3.4.0 export carries no automation filters.

## Contract version 4

Darpan 3.0.0 to 3.3.2.

### Added in 3.3.0

The facade contract stays at version 4: no method, parameter or response field is removed, and 4 public methods are added (204 to 208).

Mascot words:

- `facade.AppContentFacadeServices.get#AppContent`: the mascot entries an admin has edited, hidden or created, with a `version` hash that changes whenever they change.

Notifications by chat space:

- `facade.SettingsFacadeServices.get#NotificationRoutes`: the active tenant's chat spaces and the one space each audit update, automation, deployed script and the streak messages post to.
- `facade.SettingsFacadeServices.set#NotificationRoute`: move one of them to another space, or to none.
- `facade.SettingsFacadeServices.send#ChatSpaceTest`: post a test message to one space.

29 operator-only `admin.*` methods are added for settings, emails, scheduled jobs, retention periods, mascot words and the agent's configuration; see [Administration](/api-reference/service-catalog#administration).

### Added in 3.2.0

The facade contract stays at version 4: no method, parameter or response field is removed, and 2 public methods are added (202 to 204).

Sign-in with a passkey alone:

- `facade.AuthFacadeServices.begin#PasskeyFirstSignIn`: WebAuthn request options and a `challengeToken` for a sign-in with no password. Anonymous, rate limited per address, and the same answer for a known and an unknown username.
- `facade.AuthFacadeServices.finish#PasskeyFirstSignIn`: exchanges the token and the browser's assertion for a session, answering as `verify#SignInCode` does. Anonymous.

Changed behaviour of existing methods:

- `facade.CliAuthFacadeServices.start#CliLogin` takes an optional `scope`: `TENANT` (the default) or `ADMIN`. An `ADMIN` request is for the darpan-admin CLI; it lasts 12 hours and only a super admin with two-factor on may approve it.

### Added in 3.1.0

The facade contract stays at version 4: no 3.0.3 method, parameter or response field is removed, and 13 public methods are added (189 to 202). One existing method changes what it returns for some accounts: `login#Session` can answer a correct password with a two-factor challenge instead of a session (see below).

Two-factor sign-in:

- `facade.AuthFacadeServices.verify#SignInCode`: finishes a sign-in with the challenge token and an authenticator code, a recovery code or a passkey assertion. Anonymous.
- `facade.AuthFacadeServices.begin#TwoFactorSetup`: starts adding an authenticator app and returns its secret and QR code once. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.confirm#TwoFactorSetup`: turns the app on with its first code; returns a fresh token and, for a first factor, 10 recovery codes. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.get#TwoFactorStatus`: the caller's two-factor state, passkeys and recovery-code count.
- `facade.AuthFacadeServices.create#RecoveryCodes`: replaces the caller's recovery codes, with a fresh proof.
- `facade.AuthFacadeServices.disable#TwoFactor`: turns two-factor off, or removes only the authenticator app, with a fresh proof.

Passkeys and security keys:

- `facade.AuthFacadeServices.begin#PasskeySignIn`: WebAuthn request options for a sign-in challenge. Anonymous.
- `facade.AuthFacadeServices.begin#PasskeyRegistration`: WebAuthn creation options for a new passkey. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.finish#PasskeyRegistration`: stores the new passkey; as a first factor, turns two-factor on. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.begin#PasskeyProof`: WebAuthn request options for one action that asks for a fresh proof.
- `facade.AuthFacadeServices.rename#Passkey`: renames one of the caller's passkeys.
- `facade.AuthFacadeServices.delete#Passkey`: removes one of the caller's passkeys, with a fresh proof.

Shopify:

- `facade.ShopifyFacadeServices.begin#ShopifyInstall`: returns the Shopify authorize URL that installs the Darpan custom app registered for a store and the active tenant.

Changed behaviour of existing methods:

- `login#Session`: when the account has two-factor on, or a role requires it and it is not set up, a correct password returns `twoFactorRequired` or `twoFactorSetupRequired` with `challengeToken`, `challengeExpiresInSeconds` (300), `twoFactorMethods` and `passkeysAvailable`, and no `authToken`; `ok` is true and `authenticated` is false. A client that reads `authToken` without checking `authenticated` gets no token for these accounts. Accounts with no two-factor step sign in as before.
- The six sign-in and setup steps refuse with a completed call carrying a `reason` code: `CODE`, `PASSKEY`, `PROOF_NEEDED`, `PASSWORD`, `CHALLENGE_ENDED`, `SETUP_EXPIRED`, `PASSKEYS_UNAVAILABLE`, `PASSKEY_LIMIT`, `PASSKEY_EXISTS`, `ACCOUNT_CANNOT_SIGN_IN` or `SIGN_IN_FIRST`. `login#Session` itself has no `reason` field.
- Session lifetime: a web sign-in ends after 60 minutes with no request and at most 24 hours after sign-in, so `authTokenExpiresInSeconds` is 86400 (was 518400, 144 hours). A CLI sign-in lasts 7 days for every role (was 30 days for Darpan and tenant admins).
- `sessionInfo`, returned by `login#Session`, `get#SessionInfo`, `save#ActiveTenant`, `save#UserSettings`, `verify#OwnPassword` and `change#OwnPassword`, adds `twoFactorEnabled` and `twoFactorDueDate`.
- New passwords need at least 12 characters (was 8) in `change#OwnPassword`, `change#ExpiredPassword` and `complete#PasswordReset`. Passwords set or changed from 3.1.0 are stored with PBKDF2-HMAC-SHA256; an existing password is re-hashed at its next sign-in.
- `complete#PasswordReset` leaves two-factor on and clears a two-factor code lock.
- `request#PasswordReset`: requests with no usable client IP share one per-IP limit (20 codes an hour) instead of having none.
- `facade.CliAuthFacadeServices.approve#CliLogin` takes `code` or `passkeyAssertion`, required when the approver has two-factor on.
- Run access (tenant user, editor or tenant admin) replaces edit access for `run#Audit`, `verify#AuditFinding`, `run#Reconciliation`, `run#SavedRunDiff`, `run#GenericDiff`, `save#SftpServer`, `save#NsAuthConfig`, `delete#NsAuthConfig`, `save#NsRestletConfig`, and the save and delete methods for Shopify, HotWax OMS and database connections. `facade.AgentTurnFacadeServices.send#AgentTurn` now refuses view-only members and tenant users.
- `save#NsAuthConfig` and `save#ShopifyAuthConfig` keep a stored secret only while the token URL or shop URL is unchanged; a changed URL needs the secret again. `save#NsRestletConfig` refuses an endpoint on a different NetSuite account from its auth config.
- `list#AutomationExecutions` with no active tenant returns nothing. `delete#GeneratedOutput` deletes only the active tenant's run rows. `get#GeneratedOutput` records each download (user, tenant, file, format, size), never the contents.
- `run#ShopifyGraphqlAgentQuery` refuses a query that selects customer email, phone, name or address.
- Transport: a request carrying an HTTP Basic `Authorization` header, or `authUsername`, `authPassword` or `authUserAccount` anywhere in a JSON-RPC body or GraphQL variables, is signed out and refused with HTTP 401. The framework's `/Login`, `/SecondFactor` and `/ChangePassword` screens answer 404.

GraphQL API keys (`gql.GqlAuthServices`, outside the generated contract): `create#ApiKey` gives every key an expiry at most `gql.apiKey.maxDays` (default 90) days away, and a blank expiry gets that maximum. `rotate#ApiKey` with a blank expiry keeps the old key's expiry, brought within the maximum.

Ten operator-only `admin.*` methods are added: `admin.UserAdminServices.add#DarpanAdmin`, `remove#DarpanAdmin` and `reset#TwoFactor`; `admin.MembershipAdminServices.send#TenantWelcome`; `admin.SecurityAdminServices.get#TwoFactorPolicies`, `update#TwoFactorPolicy` and `rotate#EncryptedFields`; `admin.RetentionAdminServices.dryRun#Retention`; `admin.ShopifyAppAdminServices.list#ShopifyApps` and `save#ShopifyApp`.
