The generated contract carries `info.x-darpan-contract-version`, decoupled from the product release version. The policy is additive-only: new methods, new optional parameters, and new response fields ship without a bump; breaking changes require a conscious one. See [Contract versioning](/api-reference/json-rpc#contract-versioning).

| Contract version | Darpan releases | Public `facade.*` methods |
| --- | --- | --- |
| 5 (current) | 3.4.0, 3.4.1 | 225 |
| 4 | 3.0.0, 3.0.2, 3.0.3, 3.1.0, 3.2.0, 3.2.1, 3.3.0, 3.3.1, 3.3.2 | 208 |
| 3 | 1.5.0, 1.5.1, 2.0.0, 2.1.0 to 2.1.12 | 147 |
| 2 | 1.2.0, 1.3.0, 1.4.0 | 73 |
| 1 | 1.0.0 to 1.1.0 | 66 |

Releases 1.3.0, 1.4.0, 1.5.1, 2.1.3 to 2.1.12, 3.0.2, 3.0.3, 3.2.1, 3.3.1, 3.3.2 and 3.4.1 added or removed no methods. There is no 3.0.1 release.

<Note>
Operator-only methods (`admin.*`) are listed in the [service catalog](/api-reference/service-catalog#administration) but are not part of the public API. They serve the operator admin application and require a super-admin caller, so integrations should not depend on them. The counts below mention them only so the totals add up.
</Note>

## Contract version 5

Darpan 3.4.0. Current.

### Darpan 3.4.1

An automation keeps its own filters again (3.4.0 had it read its run's live):

- `facade.ReconciliationFacadeServices.save#Automation` takes `sources[].excludeFilters` again; a source that leaves it out keeps the filters it has. `get#Automation` sources carry `excludeFilters`. `sync#Automation` copies the run's filters, and `syncStatus.changedFields` names `FILE_1.excludeFilters` or `FILE_2.excludeFilters` when they differ.
- `facade.AgentChangeFacadeServices.apply#AuditChange` syncs each automation of the run after an exclusion, and refuses with `AUTOMATION_DRIFT` when one already differs from its run, filters included.
- `facade.TenantConfigFacadeServices.preview#TenantConfigRestore` and `admin.TransferAdminServices.import#ConfigBundle` no longer block with `AUTOMATION_FILTERS_DIFFER`. A version or bundle carries each automation's filters; one saved on 3.4.0 carries none, and each automation takes its run's.

### Darpan 3.4.0

The generated contract moves to version 5 because methods are removed: the 8 tenant script methods (`facade.TenantScriptFacadeServices` list, save, delete and run for scripts and their deployments) are gone; queries replace scripts. 25 public methods are added (208 to 225). One request field is dropped and is ignored when sent (see below). One response field of an operator-only method is renamed (see below).

Peak periods:

- `facade.PeakPeriodFacadeServices.list#PeakPeriods`, `get#PeakPeriod`, `save#PeakPeriod`, `delete#PeakPeriod`: the active tenant's busy date ranges, with peak hours, a HotWax read share and serial NetSuite reads.
- `facade.PeakPeriodFacadeServices.save#PeakPeriodRunTime`, `delete#PeakPeriodRunTime`: start an automation or audit at a set time inside a period.
- `facade.PeakPeriodFacadeServices.save#PeakPeriodSync`, `delete#PeakPeriodSync`: a sync pair's allowance and pulse for one period.

Sync pulse:

- `facade.SyncPulseFacadeServices.list#SyncPairs`, `get#SyncPair`, `save#SyncPair`, `delete#SyncPair`: a light watch on a daily check, sampling every few minutes for orders the other system has not received.
- `facade.SyncPulseFacadeServices.get#RunPulseFlags`: the records of a daily-check run the pulse had already flagged.

- `facade.SyncPulseFacadeServices.get#SyncPair`: `syncPair.periodThruDate`, the overriding peak period's last day.

Audit reads:

- `facade.AuditFacadeServices.get#AuditReadReport`: what one play of an audit read, grouped by endpoint and connection, with flags where a read cost more than it needed.

Queries (DAR-BE-334), on the moqui-jexl component:

- `facade.TenantScriptFacadeServices.list#TenantQueries`, `save#TenantQuery`, `delete#TenantQuery`, `run#TenantQuery`: the active tenant's queries, a read over what its audits keep plus a JEXL script.
- `facade.TenantScriptFacadeServices.list#TenantQuerySchedules`, `save#TenantQuerySchedule`, `delete#TenantQuerySchedule`, `run#TenantQuerySchedule`: daily schedules that email the answer and post its summary to a chat space. Saving, deleting and running one needs tenant admin; sending by hand, its owner.
- `facade.TenantScriptFacadeServices.get#TenantQueryCatalog` and `create#TenantQueryProposal`: what a query may read, and a proposed query checked against it and run first.
- `facade.AgentTurnFacadeServices.send#AgentQueryTurn`: the queries page's agent (`darpan-agent`), with the page's optional `readSpecJson` and `scriptBody`.
- Removed: `facade.TenantScriptFacadeServices.list#TenantScripts`, `save#TenantScript`, `delete#TenantScript`, `run#TenantScript`, `list#TenantScriptDeployments`, `save#TenantScriptDeployment`, `delete#TenantScriptDeployment` and `run#TenantScriptDeployment`. A client that calls one gets method not found. The 3.4.0 migration `TENANT_SCRIPTS_TO_QUERIES` copies each script into a query and each deployment into a schedule, switched off.
- `facade.SettingsFacadeServices.get#NotificationRoutes` lists a query schedule's chat delivery as the `SCRIPT` route (its `sourceId` is the schedule's id). `set#NotificationRoute` for `SCRIPT` moves that delivery, needs tenant admin, and still refuses no space.

Changed behaviour of existing methods:

- `facade.ReconciliationFacadeServices.list#Automations` adds `effectiveNextStart`, `peakPeriodName` and `peakHoursUntil` to each automation, and `facade.AuditFacadeServices.get#AuditSettings` and `save#AuditSettings` add `peakHoursUntil` to `settings`.
- `facade.AuthFacadeServices.begin#PasskeyRegistration` may leave out the code or passkey assertion within 5 minutes of a sign-in that completed two-factor, on the session it made.
- `facade.RunConclusionFacadeServices.save#RunConclusions` accepts the condition operator `LT`, less than one number.
- A CLI session may now call `save#RunConclusions`, `create#RunConclusionCode` and `sync#Automation`, the new peak period and sync pulse reads, and the ten query methods in place of the script ones. The new peak period and sync pulse saves and deletes, and `send#AgentQueryTurn`, are refused to it.
- An automation keeps no filters of its own: every run of it reads its compare scope's filters. `facade.ReconciliationFacadeServices.save#Automation` drops `sources[].excludeFilters`; a client that still sends it is not refused, and nothing is written for it. `get#Automation` sources no longer carry `excludeFilters`. `sync#Automation` no longer copies filters, and `syncStatus.changedFields` never names one.
- `facade.AgentChangeFacadeServices.apply#AuditChange` no longer refuses an exclusion with `AUTOMATION_DRIFT`. The exclusion writes the run's filter only.
- `facade.TenantConfigFacadeServices.preview#TenantConfigRestore` blocks a version made before 3.4.0 with `AUTOMATION_FILTERS_DIFFER` when an automation's own filters in it differ from its run's. Equal ones are dropped.

Operator-only `admin.*` changes, outside the public API:

- `admin.MembershipAdminServices.add#TenantMember` returns `welcomeSent` and `welcomeWithPassword` in place of `welcomeQueued`, and waits for the mail server. `send#TenantWelcome` waits too, and returns `withPassword`. The welcome email carries the temporary password while one is kept.
- `admin.RetentionAdminServices.update#RetentionPeriods` and `dryRun#Retention` take the table key `SYNC_PULSE_SAMPLE`.
- `admin.AgentConfigAdminServices.update#AgentRoleModel` takes the role `AUDIT_READ_REVIEW`.
- `admin.TransferAdminServices.import#ConfigBundle` blocks an older bundle with `AUTOMATION_FILTERS_DIFFER` on the same rule. A 3.4.0 export carries no automation filters.

## Contract version 4

Darpan 3.0.0 to 3.3.2.

### Added in 3.3.0

The facade contract stays at version 4: no method, parameter or response field is removed, and 4 public methods are added (204 to 208).

Mascot words:

- `facade.AppContentFacadeServices.get#AppContent`: the mascot entries an admin has edited, hidden or created, with a `version` hash that changes whenever they change.

Notifications by chat space:

- `facade.SettingsFacadeServices.get#NotificationRoutes`: the active tenant's chat spaces and the one space each audit update, automation, deployed script and the streak messages post to.
- `facade.SettingsFacadeServices.set#NotificationRoute`: move one of them to another space, or to none.
- `facade.SettingsFacadeServices.send#ChatSpaceTest`: post a test message to one space.

29 operator-only `admin.*` methods are added for settings, emails, scheduled jobs, retention periods, mascot words and the agent's configuration; see [Administration](/api-reference/service-catalog#administration).

### Added in 3.2.0

The facade contract stays at version 4: no method, parameter or response field is removed, and 2 public methods are added (202 to 204).

Sign-in with a passkey alone:

- `facade.AuthFacadeServices.begin#PasskeyFirstSignIn`: WebAuthn request options and a `challengeToken` for a sign-in with no password. Anonymous, rate limited per address, and the same answer for a known and an unknown username.
- `facade.AuthFacadeServices.finish#PasskeyFirstSignIn`: exchanges the token and the browser's assertion for a session, answering as `verify#SignInCode` does. Anonymous.

Changed behaviour of existing methods:

- `facade.CliAuthFacadeServices.start#CliLogin` takes an optional `scope`: `TENANT` (the default) or `ADMIN`. An `ADMIN` request is for the darpan-admin CLI; it lasts 12 hours and only a super admin with two-factor on may approve it.

### Added in 3.1.0

The facade contract stays at version 4: no 3.0.3 method, parameter or response field is removed, and 13 public methods are added (189 to 202). One existing method changes what it returns for some accounts: `login#Session` can answer a correct password with a two-factor challenge instead of a session (see below).

Two-factor sign-in:

- `facade.AuthFacadeServices.verify#SignInCode`: finishes a sign-in with the challenge token and an authenticator code, a recovery code or a passkey assertion. Anonymous.
- `facade.AuthFacadeServices.begin#TwoFactorSetup`: starts adding an authenticator app and returns its secret and QR code once. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.confirm#TwoFactorSetup`: turns the app on with its first code; returns a fresh token and, for a first factor, 10 recovery codes. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.get#TwoFactorStatus`: the caller's two-factor state, passkeys and recovery-code count.
- `facade.AuthFacadeServices.create#RecoveryCodes`: replaces the caller's recovery codes, with a fresh proof.
- `facade.AuthFacadeServices.disable#TwoFactor`: turns two-factor off, or removes only the authenticator app, with a fresh proof.

Passkeys and security keys:

- `facade.AuthFacadeServices.begin#PasskeySignIn`: WebAuthn request options for a sign-in challenge. Anonymous.
- `facade.AuthFacadeServices.begin#PasskeyRegistration`: WebAuthn creation options for a new passkey. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.finish#PasskeyRegistration`: stores the new passkey; as a first factor, turns two-factor on. Anonymous with a setup challenge token.
- `facade.AuthFacadeServices.begin#PasskeyProof`: WebAuthn request options for one action that asks for a fresh proof.
- `facade.AuthFacadeServices.rename#Passkey`: renames one of the caller's passkeys.
- `facade.AuthFacadeServices.delete#Passkey`: removes one of the caller's passkeys, with a fresh proof.

Shopify:

- `facade.ShopifyFacadeServices.begin#ShopifyInstall`: returns the Shopify authorize URL that installs the Darpan custom app registered for a store and the active tenant.

Changed behaviour of existing methods:

- `login#Session`: when the account has two-factor on, or a role requires it and it is not set up, a correct password returns `twoFactorRequired` or `twoFactorSetupRequired` with `challengeToken`, `challengeExpiresInSeconds` (300), `twoFactorMethods` and `passkeysAvailable`, and no `authToken`; `ok` is true and `authenticated` is false. A client that reads `authToken` without checking `authenticated` gets no token for these accounts. Accounts with no two-factor step sign in as before.
- The six sign-in and setup steps refuse with a completed call carrying a `reason` code: `CODE`, `PASSKEY`, `PROOF_NEEDED`, `PASSWORD`, `CHALLENGE_ENDED`, `SETUP_EXPIRED`, `PASSKEYS_UNAVAILABLE`, `PASSKEY_LIMIT`, `PASSKEY_EXISTS`, `ACCOUNT_CANNOT_SIGN_IN` or `SIGN_IN_FIRST`. `login#Session` itself has no `reason` field.
- Session lifetime: a web sign-in ends after 60 minutes with no request and at most 24 hours after sign-in, so `authTokenExpiresInSeconds` is 86400 (was 518400, 144 hours). A CLI sign-in lasts 7 days for every role (was 30 days for Darpan and tenant admins).
- `sessionInfo`, returned by `login#Session`, `get#SessionInfo`, `save#ActiveTenant`, `save#UserSettings`, `verify#OwnPassword` and `change#OwnPassword`, adds `twoFactorEnabled` and `twoFactorDueDate`.
- New passwords need at least 12 characters (was 8) in `change#OwnPassword`, `change#ExpiredPassword` and `complete#PasswordReset`. Passwords set or changed from 3.1.0 are stored with PBKDF2-HMAC-SHA256; an existing password is re-hashed at its next sign-in.
- `complete#PasswordReset` leaves two-factor on and clears a two-factor code lock.
- `request#PasswordReset`: requests with no usable client IP share one per-IP limit (20 codes an hour) instead of having none.
- `facade.CliAuthFacadeServices.approve#CliLogin` takes `code` or `passkeyAssertion`, required when the approver has two-factor on.
- Run access (tenant user, editor or tenant admin) replaces edit access for `run#Audit`, `verify#AuditFinding`, `run#Reconciliation`, `run#SavedRunDiff`, `run#GenericDiff`, `save#SftpServer`, `save#NsAuthConfig`, `delete#NsAuthConfig`, `save#NsRestletConfig`, and the save and delete methods for Shopify, HotWax OMS and database connections. `facade.AgentTurnFacadeServices.send#AgentTurn` now refuses view-only members and tenant users.
- `save#NsAuthConfig` and `save#ShopifyAuthConfig` keep a stored secret only while the token URL or shop URL is unchanged; a changed URL needs the secret again. `save#NsRestletConfig` refuses an endpoint on a different NetSuite account from its auth config.
- `list#AutomationExecutions` with no active tenant returns nothing. `delete#GeneratedOutput` deletes only the active tenant's run rows. `get#GeneratedOutput` records each download (user, tenant, file, format, size), never the contents.
- `run#ShopifyGraphqlAgentQuery` refuses a query that selects customer email, phone, name or address.
- Transport: a request carrying an HTTP Basic `Authorization` header, or `authUsername`, `authPassword` or `authUserAccount` anywhere in a JSON-RPC body or GraphQL variables, is signed out and refused with HTTP 401. The framework's `/Login`, `/SecondFactor` and `/ChangePassword` screens answer 404.

GraphQL API keys (`gql.GqlAuthServices`, outside the generated contract): `create#ApiKey` gives every key an expiry at most `gql.apiKey.maxDays` (default 90) days away, and a blank expiry gets that maximum. `rotate#ApiKey` with a blank expiry keeps the old key's expiry, brought within the maximum.

Ten operator-only `admin.*` methods are added: `admin.UserAdminServices.add#DarpanAdmin`, `remove#DarpanAdmin` and `reset#TwoFactor`; `admin.MembershipAdminServices.send#TenantWelcome`; `admin.SecurityAdminServices.get#TwoFactorPolicies`, `update#TwoFactorPolicy` and `rotate#EncryptedFields`; `admin.RetentionAdminServices.dryRun#Retention`; `admin.ShopifyAppAdminServices.list#ShopifyApps` and `save#ShopifyApp`. Existing operator methods change: `add#TenantMember` takes `sendWelcome` and returns `welcomeQueued`; `get#UserList` takes `darpanAdminsOnly` and returns `darpanRoles` and `twoFactor`; `get#UserDetail` returns `darpanRoles` and two-factor fields; `export#ConfigBundle` and `begin#SecretHandoff` need `twoFactorCode` or `twoFactorPasskeyAssertion` from a caller with two-factor on.

## Contract version 3

Darpan 1.5.0 to 2.1.12.

### Added in 2.1.2

The facade contract stays at version 3: every 2.1.1 method, parameter and response field is unchanged, and 2 public methods are added (145 to 147).

- `facade.AuditFacadeServices.retry#AuditCheck`: re-runs one audit check that did not run on one morning, from the files that morning's run already read.
- `facade.ReconciliationFacadeServices.get#ActiveRunResult`: the active tenant's newest pending or running run of a saved run, begun in the last two minutes.

Rules gain two FIELD_COMPARISON operators, `all in` and `contains all`, for comma-separated lists; a rule's `expression` names them in `operator`.

### Added in 2.1.1

The facade contract stays at version 3: every 2.1.0 method, parameter and response field is unchanged, and 4 public methods are added (141 to 145).

- `facade.AuditFacadeServices.get#AuditProgress`: whether an audit's play is running, and how far its checks have got.
- `facade.ReconciliationFacadeServices.get#AutomationStreaks`: an automation's stored clean-day streak, its badges and side quests.
- `facade.ReconciliationFacadeServices.retry#AutomationExecutionFromExtracts`: re-runs a failed execution whose reads all finished, over the same window, from the files it already read.
- `facade.ReconciliationFacadeServices.repair#ConnectorRecordKeys`: adds the record root to the bare keys of a run's connector sources; `dryRun` lists the changes without saving them.

`facade.AuthFacadeServices.request#PasswordReset` returns two new fields: `outcome` (`sent`, `noAccount`, `locked`, `noEmail`, `overLimit` or `sendFailed`) and `emailAddressMasked`.

Five operator-only `admin.*` methods are added: `get#LiveOperations`, `get#TransferCatalog`, `export#ConfigBundle`, `import#ConfigBundle` and `begin#SecretHandoff`.
