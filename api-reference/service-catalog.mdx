title: "Service catalog"
description: "Verified backend facade services exposed through Darpan JSON-RPC."
---

Every method below is called as the JSON-RPC `method` value. The generated contract builds this list from the services marked for remote calls in `service/facade/` and `service/admin/` of the Darpan backend component, plus `service/facade/` and `service/admin/` of the integration components. `facade.*` methods are the public API. `admin.*` methods are operator-only and listed under [Administration](#administration); they are not part of the public API.

This catalog matches Darpan 3.4.0 (contract version 4).

All methods require an authenticated session unless noted. Eighteen methods accept anonymous calls, so a caller can sign in, finish a two-factor step, end a session or reset a forgotten password: `login#Session`, `logout#Session`, `get#SessionInfo`, `change#ExpiredPassword`, `request#PasswordReset`, `verify#PasswordResetCode`, `complete#PasswordReset`, `get#PasswordResetStatus`, `verify#SignInCode`, `begin#TwoFactorSetup`, `confirm#TwoFactorSetup`, `begin#PasskeySignIn`, `begin#PasskeyFirstSignIn`, `finish#PasskeyFirstSignIn`, `begin#PasskeyRegistration` and `finish#PasskeyRegistration` in `facade.AuthFacadeServices`, and `start#CliLogin` and `poll#CliLogin` in `facade.CliAuthFacadeServices`. Without a session, the six two-factor methods act only for the account named by a challenge token that `login#Session` returned.

## Auth (`facade.AuthFacadeServices`)

| Method | Purpose |
| --- | --- |
| `login#Session` | Check a username and password. For an account with no two-factor step, create a session and return the login-key token (`authToken`) and `sessionInfo`. For an account with two-factor on, or required by its role and not set up, return `twoFactorRequired` or `twoFactorSetupRequired` with a `challengeToken`, `challengeExpiresInSeconds` (300), `twoFactorMethods` (`app`, `passkey`) and `passkeysAvailable`, and no session: `ok` is true and `authenticated` is false, so decide on `authenticated`. Anonymous. |
| `logout#Session` | Revoke the token on the current request and end that session only. Anonymous-safe. |
| `logout#AllSessions` | Revoke every login key for the current user, signing them out on every device. |
| `get#SessionInfo` | Return current session, user, and active-tenant context, including `twoFactorEnabled` and, while two-factor is due and not on, `twoFactorDueDate`. A login key past its idle or absolute limit, or issued before the account's last two-factor change, restores no session. Anonymous-safe. |
| `save#ActiveTenant` | Switch the caller's active tenant. The choice is stored on the user, not the session, so it applies to every session and tab of that user. The tenant key is the tenant's user group id (`companyUserGroupId` on tenant-owned records). |
| `save#UserSettings` | Save per-user settings, including display name and preferred display timezone (IANA id; empty string clears the preference). Returns refreshed session metadata. |
| `verify#OwnPassword` | Re-verify the current user's password. |
| `change#OwnPassword` | Change the current user's password. Requires the current password; a wrong one counts as a failed login. The new password needs at least 12 characters. Every login key of the user ends on success. |
| `change#ExpiredPassword` | Change the password of an account that cannot sign in until it is changed, without a session. Requires the account's current password. Anonymous. Issues no token: sign in again afterwards. |
| `request#PasswordReset` | Email a 6-digit reset code to the email on file for a username or email address, and report what happened in `outcome` (`sent`, `noAccount`, `locked`, `noEmail`, `overLimit` or `sendFailed`), with the masked address when sent. Limits: 3 codes an hour per account and 20 an hour per client IP; requests with no usable client IP share one limit. The code expires in 15 minutes; a new request replaces it. Anonymous. |
| `verify#PasswordResetCode` | Check a reset code without using it up. Five wrong guesses end the code; wrong guesses do not count as failed logins. Every failure returns the same error. Anonymous. |
| `complete#PasswordReset` | Set a new password (at least 12 characters) with a reset code, then sign the account out on every device and email it that the password changed. Two-factor stays on; a two-factor code lock is cleared. Password-policy failures are reported in full. A disabled account is refused and stays disabled. Anonymous. Issues no token: sign in again afterwards. |
| `get#PasswordResetStatus` | Whether this deployment can send reset email: true when the `SYSTEM` email server has an SMTP host and the reset-code email template is loaded. Anonymous. |
| `save#RecoveryEmail` | Set the signed-in user's recovery email, where reset codes go. Requires the current password; a wrong one counts as a failed login. Refused when another account already uses the address. The new address, and the previous one when it changes, get a notice. Returns the address masked. |
| `verify#SignInCode` | Finish a sign-in that `login#Session` answered with `twoFactorRequired`: send the `challengeToken` with a 6-digit authenticator `code`, a `recoveryCode`, or a `passkeyAssertion` over `begin#PasskeySignIn`'s options. Success returns what a password sign-in returns (`authToken`, `sessionInfo`); a used recovery code returns `recoveryCodesLeft` and emails the account. Anonymous. |
| `begin#TwoFactorSetup` | Start adding an authenticator app: return a new secret, its `otpauthUri` and a QR code (`qrDataUri`), in this reply only, to confirm within 15 minutes. Accepts a setup `challengeToken` from `login#Session`, or a signed-in caller with `currentPassword` (no factor yet) or a current code or passkey assertion (two-factor on). Anonymous with a challenge token. |
| `confirm#TwoFactorSetup` | Turn the authenticator app on with the first code it shows. Every other session and CLI key of the account ends and the caller receives a fresh `authToken`; with a setup challenge this is the sign-in. Returns 10 recovery codes, once, when no factor was on before. Anonymous with a challenge token. |
| `get#TwoFactorStatus` | The caller's two-factor state: on or off, the authenticator app, each passkey (name, created, last used, synced), unused recovery codes, whether a role requires it and from when, and whether code entry is locked. Never returns the secret. |
| `create#RecoveryCodes` | Replace the caller's recovery codes with 10 new ones, returned once. Needs a current authenticator code or a passkey assertion. |
| `disable#TwoFactor` | Turn two-factor off (the app and every passkey) with a current code or passkey assertion; refused when a role of the caller requires it. Every session and CLI key ends and the reply carries a fresh `authToken` for the caller. With `appOnly` and a passkey left, removes only the app and ends no session. |
| `begin#PasskeySignIn` | WebAuthn request options (`publicKeyOptions`, JSON text) for a sign-in challenge whose `twoFactorMethods` include `passkey`. Send the browser's assertion to `verify#SignInCode` with the same `challengeToken`. Anonymous. |
| `begin#PasskeyFirstSignIn` | Start a sign-in with a passkey alone, no password. Optional `username`. Returns `publicKeyOptions` (WebAuthn request options, JSON text, user verification required), a `challengeToken` held in page memory and good for one finish, and `expiresInSeconds` (300). With a username, the options list that account's passkeys; for a username with no passkey they carry one decoy credential, so the answer never says whether the account exists. With no username the list is empty and the browser offers its own passkeys. At most 10 starts a minute from one address. Optional `scope`: `TENANT` (the default) or `ADMIN`, the darpan-admin CLI, which may call `admin.*` for 12 hours and which only a super admin may approve. Anonymous. |
| `finish#PasskeyFirstSignIn` | Finish a passkey-alone sign-in: send the `challengeToken` and the browser's `passkeyAssertion`. Success answers as `verify#SignInCode` does (`authToken`, `sessionInfo`). The token is spent by the call whatever happens, so start again after a refusal. `reason` is `PASSKEY_REFUSED`, `ACCOUNT_CANNOT_SIGN_IN`, `PASSWORD_CHANGE_REQUIRED` (sign in with the password first) or `PASSKEYS_UNAVAILABLE`. Anonymous. |
| `begin#PasskeyRegistration` / `finish#PasskeyRegistration` | Register a passkey or security key. `begin` returns WebAuthn creation options, valid 5 minutes, after the same check `begin#TwoFactorSetup` makes, except that within 5 minutes of a sign-in that completed two-factor (`verify#SignInCode`, `finish#PasskeyFirstSignIn`) the session it made may leave out the code or passkey assertion; `finish` stores the browser's credential under a name (60 characters at most), emails the account, and returns `passkeyId`. Up to 10 per account; as the first factor it turns two-factor on as `confirm#TwoFactorSetup` does (sessions end, fresh `authToken`, 10 recovery codes); anonymous with a setup challenge token. |
| `begin#PasskeyProof` | WebAuthn request options over the caller's passkeys for one action that asks for a fresh proof, such as `create#RecoveryCodes`, `disable#TwoFactor`, `delete#Passkey` or `facade.CliAuthFacadeServices.approve#CliLogin`. The resulting assertion is single-use and valid 5 minutes. |
| `rename#Passkey` | Rename one of the caller's passkeys (60 characters at most). Needs no fresh proof. |
| `delete#Passkey` | Remove one of the caller's passkeys with a current code or passkey assertion. Removing the last factor is refused when a role requires two-factor; otherwise it turns two-factor off as `disable#TwoFactor` does. |

The password reset methods need the password reset email templates loaded and an email server configured on the deployment. Without both, no code is sent and `get#PasswordResetStatus` returns false.

Two-factor sign-in runs in two calls. `login#Session` checks the password; when the account has two-factor on, it returns a `challengeToken` instead of a session, and `verify#SignInCode` exchanges that token and a code (or a passkey assertion from `begin#PasskeySignIn`) for the session. When a role requires two-factor and the account has none, `login#Session` returns `twoFactorSetupRequired`; the token then works only with `begin#TwoFactorSetup` and `confirm#TwoFactorSetup`, or `begin#PasskeyRegistration` and `finish#PasskeyRegistration`, and the confirming call signs the account in. A challenge token lives 300 seconds, is used once, and ends after five wrong answers.

The sign-in and setup steps (`verify#SignInCode`, `begin#TwoFactorSetup`, `confirm#TwoFactorSetup`, `begin#PasskeySignIn`, `begin#PasskeyRegistration`, `finish#PasskeyRegistration`) answer a refusal as a completed call: `ok` false, the message in `errors`, `challengeEnded` where it applies, and a `reason` code: `CODE`, `PASSKEY`, `PROOF_NEEDED`, `PASSWORD`, `CHALLENGE_ENDED`, `SETUP_EXPIRED`, `PASSKEYS_UNAVAILABLE`, `PASSKEY_LIMIT`, `PASSKEY_EXISTS`, `ACCOUNT_CANNOT_SIGN_IN` or `SIGN_IN_FIRST`. Branch on `reason`, not on the message text. The other two-factor methods refuse with a JSON-RPC error.

Authenticator codes are 6 digits on a 30-second step, accepted one step either side, and a code is accepted once. Each wrong authenticator or recovery code counts as a failed login toward the account lockout. Twenty wrong codes in 24 hours lock code entry until a password reset or an operator reset, and the account is emailed. Recovery codes are single-use; a password reset leaves two-factor on.

Two-factor is optional for every account and can be required by role: `ADMIN`, `DARPAN_SUPER_ADMIN`, `DARPAN_ADMIN`, and tenant admin in any tenant. An operator sets the date a role requires it from; before that date, `sessionInfo.twoFactorDueDate` shows when it becomes due and sign-in still issues a session. Passkeys are offered only when the deployment has a WebAuthn relying party configured (`passkeysAvailable`).

A web sign-in ends after 60 minutes with no request and at most 24 hours after sign-in; `authTokenExpiresInSeconds` reports the 24-hour limit. A CLI sign-in lasts 7 days for every role. Turning two-factor on or off ends the account's other sessions and CLI keys, and a CLI key of an account that a role now requires two-factor for, and that has none, is refused.

## CLI sign-in (`facade.CliAuthFacadeServices`)

The Darpan CLI signs in with a device code. The CLI starts and polls without a session, and the person approves the sign-in in the Darpan app while signed in as themselves. The key the CLI receives is marked as a CLI session, and the server holds it to an allowlist: getters that write nothing and return no credential, the run starters, the query and schedule methods (not `send#AgentQueryTurn`), `logout#CliSession`, and three edits that already need tenant write access: `facade.RunConclusionFacadeServices.save#RunConclusions` and `create#RunConclusionCode`, and `facade.ReconciliationFacadeServices.sync#Automation`. Every other method is refused to a CLI session, including the peak period and sync pair saves and deletes.

| Method | Purpose |
| --- | --- |
| `start#CliLogin` | Start a CLI sign-in. Returns the device code the CLI polls with and the user code (`XXXX-XXXX`) the person approves in the app; both expire in 10 minutes. At most 10 starts a minute from one address. Anonymous. |
| `poll#CliLogin` | Ask whether a sign-in was approved: `PENDING`, `APPROVED`, `DENIED` or `EXPIRED`. The first poll after approval returns the login key and claims the request; any later poll answers `EXPIRED`. Anonymous. |
| `get#CliLoginRequest` | What a waiting sign-in asks for, by user code: the computer name the CLI reported, its status and its expiry, so the person can check it before approving. |
| `approve#CliLogin` / `deny#CliLogin` | Approve a waiting sign-in as the signed-in person, so the CLI's next poll gets a login key for them, or deny it, so no key is issued. Refused from a CLI session. Approval is also refused when the CLI is not on for the account, and needs a current two-factor code or a passkey assertion when the approver has two-factor on. |
| `list#CliSessions` / `revoke#CliSession` | The signed-in person's own CLI sessions that still work, newest first, or end one of them; its key stops working at once. |
| `logout#CliSession` | Sign the calling CLI out by revoking the CLI session whose key the request carries. Refused for a request that is not a CLI session. |

### CLI access (`facade.CliAccessFacadeServices`)

A Darpan admin turns the CLI on per user and tenant (see CLI access under [Administration](#administration)). Neither method is callable from a CLI session.

| Method | Purpose |
| --- | --- |
| `get#MyCliAccess` | The signed-in person's CLI state in the active tenant (`LIVE`, `PAUSED`, `ENDED`, `NOT_GRANTED` or `DARPAN_ADMIN`), the grant's end, how long a CLI sign-in lasts there, and their latest request. |
| `request#CliAccess` | Ask a Darpan admin to turn the CLI on for the signed-in person in the active tenant, with an optional reason (at most 500 characters). Asking again while a request is open updates its reason. Refused for a Darpan admin, when the CLI is already on there, or when the person is not a member of the tenant. |

## Peak periods (`facade.PeakPeriodFacadeServices`)

A peak period is a date range a tenant marks as busy, such as a sale. Inside it, Darpan holds scheduled runs out of the period's peak hours, starts the runs it moves at their set time, caps HotWax reads at a share of the normal rate, and can send NetSuite reads one at a time. Dates and hours are in the tenant's time zone. Writes need edit access on the active tenant.

| Method | Purpose |
| --- | --- |
| `list#PeakPeriods` | The active tenant's peak periods, each with its state in the tenant's today: `upcoming`, `on`, `off` or `ended`. |
| `get#PeakPeriod` | One peak period with its run-time moves, the runs its peak hours or a sync lag allowance hold, the runs a move can name, and its sync pair overrides. |
| `save#PeakPeriod` | Create or update a peak period: name, first and last day, peak hours (`HH:mm`, both set or both blank), `hotwaxReadSharePct` and `netsuiteSerial`. Active periods may not overlap. An omitted share or omitted peak hours clear them; an omitted `netsuiteSerial` keeps the stored value. |
| `delete#PeakPeriod` | Delete a peak period with its run-time moves and sync overrides. |
| `save#PeakPeriodRunTime` / `delete#PeakPeriodRunTime` | Make a run (an automation or an audit) start at `runTime` on `onDate`, or on every day of the period when `onDate` is blank, or remove that move. |
| `save#PeakPeriodSync` / `delete#PeakPeriodSync` | Replace or remove one sync pair's override for the period: the allowance (15 minutes to 48 hours) and the pulse (0, 60, 120, 180, 240 or 360 minutes; 0 is off for the period). Each blank value means the pair's normal one. A save refuses a pulse on a check the pulse cannot read. |

## Sync pulse (`facade.SyncPulseFacadeServices`)

A sync pair attaches a light watch to an existing daily check: every few minutes the pulse reads the check's upstream side for a short window, asks the other side by key which of those orders it holds, and records a sample. An order still missing past the pair's allowance is tracked until it arrives. The daily check also waits for the allowance before it reads a day. A pulse needs HotWax orders upstream. Writes need edit access on the active tenant.

| Method | Purpose |
| --- | --- |
| `list#SyncPairs` | The active tenant's sync pairs, with the waiting and past-allowance counts from the latest sample and the open orders. |
| `get#SyncPair` | One sync pair: its allowance and pulse in force today and its own values, today's samples, and the open past-allowance orders, oldest first. Always returns the daily checks and chat spaces the pair form picks from; with no `syncPairId` that is all it returns. |
| `save#SyncPair` | Create or update a sync pair: the automation (one pair per automation), the upstream side, the allowance, the pulse cadence, a chat space and an hourly summary. A blank cadence is pulse off and a blank chat space is none; `isActive` and `hourlySummary` keep their stored values when omitted. |
| `delete#SyncPair` | Delete a sync pair with its peak period overrides, samples and tracked orders. |
| `get#RunPulseFlags` | For one daily-check run, the records the pulse had already flagged past allowance before the run started and that were still open then, each with the time the pulse first flagged it. Empty, with no `syncPairId`, when the run's check has no pair. |

`get#SyncPair`'s `syncPair` also carries `periodThruDate`: the last day (a date, tenant-local) of the peak period that overrides the pair today, or empty when no period applies.

## Audits (`facade.AuditFacadeServices`)

An audit is a set of statements about the active tenant's data, each tested by checks that run on a daily schedule and record findings. Reports and findings are returned as `darpan.audit.report/v1` and `darpan.audit.finding/v1` documents. Another tenant's audit or finding reads as not found. Writes need edit access on the active tenant.

| Method | Purpose |
| --- | --- |
| `get#Audits` | The active tenant's audits: id (the audit's code), name, and the period one report covers. |
| `create#Audit` | Create an audit from a name and a period (`day`, `month` or `quarter`). Its id is the name in lower case with dashes, unique within the tenant; `new` is refused. Statements and checks are added afterwards. |
| `add#AuditStatement` | Add a statement to an audit: the text that must be true, a category (`orders`, `refundsAndCredits`, `returns` or `exchangesAndWarranty`), and a weight (`firm`, or `derived` while awaiting the tenant's confirmation; default `derived`). It gets the next statement code, is placed last, and is active. |
| `get#AuditSettings` / `save#AuditSettings` | Read or change an audit's name, its statements' text and on/off state, and the daily schedule (time and time zone) its checks run on. A save sends only the statements that changed, creates a paused automation for any check whose run has none, and returns the settings as saved. The read also returns each statement's checks, the earliest day `run#Audit` can record, and, while the tenant is inside a peak period's peak hours, `peakHoursUntil`. |
| `get#AuditCheckOptions` | What the add-a-check editor offers for one audit: its statements, the tenant's saved runs with their rules and conclusions, the row types and fix systems a check may name, and the audit's existing checks. |
| `save#AuditCheck` | Create or update a check and replace its links to the audit's statements; at least one link is required. All or nothing. Refused, with the reason, for a statement outside the audit, a run the tenant does not own, a rule not in that run, or a row type the check cannot record. A new check, or one whose run changed, has no automation until `run#Audit` or `save#AuditSettings` creates one. |
| `run#Audit` | Run every check of the audit now over a range of days, first to last inclusive, in the tenant's time zone, recording findings as the scheduled run does. Submitted in the background, one automation per run; returns each submission. Refused before anything runs for days in the future, a backwards range, or a period that ended and was not extended. With `fullRead`, every system is read for the whole range; without it, each check reads the days since its last complete read and re-checks its older open findings by key. |
| `get#AuditReport` | An audit's report for one day (default today in the tenant's time zone), optionally for one period's run, as a `darpan.audit.report/v1` document. |
| `get#AuditFindingsByOrder` | Every open and pending finding of one audit, one entry per order with its lines and the line holding it up, each with its statement and category. Filters by statement, period, and state (`open` or `pending`). State is as of today. |
| `get#AuditFinding` | One finding as a `darpan.audit.finding/v1` document: records, evidence, fix and history. |
| `verify#AuditFinding` | Re-check one finding's record now: its check runs for that record only, reading each system by key, and the finding is closed if the problem is gone or refreshed with today's cause. Submitted in the background; `get#AuditFinding` shows the result once `lastChecked` changes. Records no check run, so the check's health and next read are unchanged. Refused when the check has no automation yet. |
| `get#AuditCheckExtracts` | The files each system's read wrote for one check, day and period: one row per side with the system, the record count, and the file's data-manager path. Empty when the check has no recorded run for that day and period. |
| `get#AuditProgress` | What an audit's checks are doing now: each automation with a run in progress or queued, the checks it feeds, its stage and progress, and whether it looks healthy, slow or stuck against its own last successful run. Cheap enough to poll while a play or the morning run is going. |
| `get#AuditReadReport` | What one play of an audit read, by audit code and optional morning and period: its reads grouped by endpoint and connection (reads, records, the checks that read, each read's window, the call tally), the totals, and flags where a read cost more than it needed (`DUPLICATE_READ`, `WHOLE_PERIOD_READ`, `LOOKUP_OVER_SHARE`, `LOOKUP_EVERY_PLAY`, `THROTTLED`, `CALLS_GREW`). The thresholds are the Audit reads settings. Empty when the audit has not played. |
| `retry#AuditCheck` | Retry from last read: re-runs one check that did not run on one morning, from the files that morning's run already read. Refused, with the reason, when the check is not the audit's, already ran, has no run that morning, or its reads did not finish. |

## Audit agent (`facade.AgentTurnFacadeServices`)

The audit agent answers questions about an audit and drafts changes to it. It works in the session's active tenant, fixed for the whole request. A person needs a live grant of AI access in that tenant, given by a Darpan admin, and edit access to the tenant. Ships in the `darpan-agent` component.

| Method | Purpose |
| --- | --- |
| `send#AgentTurn` | Send one message about an audit (by `auditId` or `auditCode`), optionally with a finding open. Questions are answered; comments on causes and rules become one draft change for a person to approve, or a ticket for Darpan staff. Keys, secrets, emails and phone numbers are masked before anything is stored or sent. `outcome` reports a refusal, such as no live grant, the per-person hourly message limit (`RATE_LIMITED`) or the tenant's daily budget (`OVER_BUDGET`). |
| `get#AgentStatus` | Whether the agent can run for the person now (`state`), their AI access in the tenant (`grantState`: `LIVE`, `NOT_GRANTED`, `EXPIRED` or `PAUSED`), and whether they may approve its changes (`canApprove`). |
| `get#AgentConversation` | The person's own conversation: its messages and its proposals with their status now. Another person's or another tenant's conversation reads as not found. |
| `send#AgentQueryTurn` | One message from the queries page, with the page's `readSpecJson` and `scriptBody` (optional, masked, 8,000 characters each) so the agent builds on the person's edits. The agent reads `facade.TenantScriptFacadeServices.get#TenantQueryCatalog` and proposes one query through `facade.TenantScriptFacadeServices.create#TenantQueryProposal`, so `queryProposal` (`proposal`, `preview`) has already run; or it asks one question (`question`), or answers that the data is not kept. Nothing is saved. Its model sees ids, field names, counts and error kinds, never rows or summaries. Same gates and `outcome` values as `send#AgentTurn`. A query conversation never continues as an audit one. |

### Proposed changes (`facade.AgentChangeFacadeServices`)

The agent only drafts changes. A person with edit access on the active tenant plans, applies, rejects or reverts them. Another tenant's proposal reads as not found.

| Method | Purpose |
| --- | --- |
| `plan#AuditChange` | Plan an open proposal again against the current config: the change runs through its real save, which is rolled back, and `planHash` covers the change and the config it was planned against. Ends `PLANNED`, or `INVALID` with the save's refusal. |
| `apply#AuditChange` | Apply a planned proposal by its `planHash`, through the save the app uses, keeping a config version before and after. Refused for a `BLOCKED` proposal (record ids that did not come from the person, the finding or the config). An exclusion writes the run's filter only. When the config changed since the plan, the proposal turns `STALE` and nothing is written. |
| `reject#AuditChange` | Decline an open proposal, with an optional reason; it can no longer be applied. |
| `revert#AuditChange` | Create a planned proposal that puts back what an applied proposal changed, applied like any other. Refused when that setting changed again after the apply, or when a revert is already open. |
| `list#BrainChangeTickets` | The active tenant's tickets for Darpan staff (requests that need code, such as a new cause or a missing field), newest first, optionally in one status. |

## Config versions (`facade.TenantConfigFacadeServices`)

The active tenant's audit config (audits, statements, checks, runs, queries, conclusion codes and connections) kept as numbered versions. Another tenant's version reads as not found.

| Method | Purpose |
| --- | --- |
| `snapshot#TenantConfig` | Keep the current config as a new version when it changed since the latest one, with an optional reason. Needs edit access. |
| `get#TenantConfigVersions` / `get#TenantConfigVersion` | The tenant's versions, newest first (at most 500), or one version with its pack, the whole-tenant transfer bundle. |
| `preview#TenantConfigRestore` | What restoring a version would do, writing nothing: what the version holds is put back, statements added since are switched off, check links added since are removed, and runs added since are kept. Returns the plan and its `planHash`. A version made before 3.4.0 is blocked with `AUTOMATION_FILTERS_DIFFER` when an automation's own filters in it differ from its run's; equal ones are dropped. |
| `restore#TenantConfigVersion` | Apply exactly the previewed plan, by its `planHash`: the current config is kept as a version first, then the restore is written and kept as a version. One transaction. Refused when the plan has blocking items or no longer matches the config. Needs edit access. |

## Queries (`facade.TenantScriptFacadeServices`)

A query is a read over what the tenant's audits keep (a dataset's kept fields, a saved run's newest result, an audit's findings) plus a JEXL script, run on the moqui-jexl component with the `QUERY` limits. A schedule runs a saved query daily and delivers its answer by email (the summary and up to five CSV files) and to a chat space (the summary). From 3.4.0 these replace the script methods. Every read and write names the active tenant, so another tenant's query or schedule reads as not found. Writing and running need edit access; schedules need tenant admin, because they send the tenant's data out. See [Tenant queries](/backend/tenant-queries).

| Method | Purpose |
| --- | --- |
| `list#TenantQueries` | The tenant's queries by name, each with its read in words (`readText`), plus the `fn:` library and the `QUERY` limits for the editor. |
| `save#TenantQuery` | Create or update a query (`tenantQueryId`, `queryName`, `description`, `readSpecJson`, `scriptBody`). Names are unique in the tenant. The script must parse and run on its sample input, and the read's sources must exist. Stored only for the caller's active tenant. A query with a schedule needs tenant admin to change, and saving it makes the caller the schedule's owner. |
| `delete#TenantQuery` | Delete a query with its schedules and their deliveries. A query with a schedule needs tenant admin. |
| `run#TenantQuery` | Run a saved query, or the read and script given (a draft of a saved query runs as written), on the tenant's data now. Nothing is sent. `result`: `summary`, `files` (`name`, `columns`, `rowCount`, up to 20 `previewRows`), `data`, `nothing`, `invalid`, `readCounts`, `units`, `elapsedMs`, `logs`, `error` (`kind`, `message`, `line`), `readText`. A read or script failure is in `result.error`, not a service error. |
| `get#TenantQueryCatalog` | What the tenant's queries may read: its active datasets (with `fields`, or `wholeRecords`), its saved runs, and its audits with the finding fields. |
| `create#TenantQueryProposal` | Check a proposed query's read against the catalog and, when every source and field is in it, run it. Nothing is saved. `status` `PROPOSED` with `proposal` and `preview` (as `run#TenantQuery`'s result), or `REFUSED` with `code` `NOT_KEPT`, `UNKNOWN_SOURCE` or `INVALID_READ` and the `field`. |
| `list#TenantQuerySchedules` | The tenant's schedules (optionally for one query): cron and zone, `isActive`, owner, email recipients and chat space, next and last run with status and message, each delivery's last outcome; plus the tenant time zone. |
| `save#TenantQuerySchedule` | Create or update a schedule: `dailyAt` (`HH:mm`) or `cronExpression`, read in the tenant's zone; `emailTo`, `emailCc` (at most 50 addresses together) and `chatSpaceId` (the tenant's, switched on), at least one; `isActive` (default false). Whoever saves it owns it, and it sends as them. Needs tenant admin. |
| `delete#TenantQuerySchedule` | Delete a schedule and its deliveries. Needs tenant admin. |
| `run#TenantQuerySchedule` | Run a schedule now. With `send` false (the default) it is a preview: the saved query runs as the caller, `message` says where it would go, and nothing is delivered or recorded. With `send` true it delivers and records the run; only its owner may. Needs tenant admin. `outcome`: `status`, `message`, `result`, `readCounts`, `deliveries`. |

## Data source definitions (`facade.DataSourceDefinitionFacadeServices`)

A data source definition describes a GraphQL or REST JSON read that connectors run. Definitions are platform config that every tenant's runs read, so these methods are super-admin only and are not callable from a CLI session. A definition is never edited in place: a save makes a new `DRAFT` version of its family, and an `ACTIVE` version keeps its document. Saves and retirements are recorded in the admin audit log.

| Method | Purpose |
| --- | --- |
| `validate#DataSourceDefinition` | Check a definition document for a protocol (`GRAPHQL` or `REST_JSON`) and list every problem. Saves nothing. |
| `create#DataSourceDefinition` | Save a definition as a new `DRAFT` row: the first version of a new family (`definitionId`, stored as `<definitionId>_V1`), or the next version of an existing one (`basedOnId`), leaving earlier rows as they are. A document with any problem is refused with all of them. |
| `retire#DataSourceDefinition` | Mark a definition `RETIRED`, kept for history. Refused while a connector still reads it; retiring a retired row changes nothing. |

## Agent queries (`facade.AgentFacadeServices`)

A tenant user's agent, for example through the Darpan CLI, can send fresh read-only queries to the tenant's own NetSuite, HotWax OMS and Shopify systems through connections the active tenant stores. A connection shared from another tenant is refused. The query methods ship in the integration components (see below). Each call has a 60-second limit and a 5 MB response limit, credentials are never returned, a busy instance answers `THROTTLED` with `retryAfterSeconds`, and every attempt is logged for the tenant.

| Method | Purpose |
| --- | --- |
| `list#AgentQueryLogs` | The fresh queries agents sent to the tenant's systems, newest first and paged, optionally by outcome (`OK`, `REFUSED`, `THROTTLED`, `ERROR` or `TIMEOUT`). Tenant admins only. |

## Administration

<Warning>
Operator-only. The `admin.*` methods below are not part of the public API, and integrations should not depend on them. A non-super-admin caller is denied before the service body runs.
</Warning>

## Per-method reference

The machine-readable contract for the public methods lives in the
[generated OpenAPI reference](/api-reference/openapi.json), regenerated from the backend
facade XML (`./gradlew :runtime:component:darpan:generateApiContract`). Backend CI runs
`scripts/check_service_catalog.py` from this docs repo against the generated method list
(`docs/api-contract/methods.txt`): it fails when this catalog names a method the contract
does not define, and only reports, without failing, contract methods the catalog does not
list. How to read the reference:

- Each method has four schemas in `components.schemas`, named from its verb#noun:
  `<VerbNoun>Params` (request parameters, with `required` markers), `<VerbNoun>Result`
  (the response payload the hand-written UI types model), and the `...Request`/`...Response`
  JSON-RPC envelopes around them.
- Parameter and field descriptions come straight from the service definitions.
- Error behavior is uniform. A failed call returns the `JsonRpcError` object; a service
  that ends with errors returns code `500` with HTTP 500. See [Errors](/api-reference/errors).

For the transport contract used by all methods above, see [JSON-RPC transport](/api-reference/json-rpc).
