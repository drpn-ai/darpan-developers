title: "Reconciliation engine"
description: "How Darpan turns source data into generated reconciliation output."
---

This is where a run actually spends its time, so the two passes — base diff and rule evaluation — are worth understanding before making engine changes.

The reconciliation engine is the run pipeline. It stages source data, normalizes records, compares matching keys, applies rules, and writes generated output for review.

## High-level flow

```text
UI workflow
  -> JSON-RPC facade service
  -> access and tenant checks
  -> saved run, RuleSet, mapping, or source records
  -> source data staging
  -> Keep in Spark (records set aside, not compared)
  -> Spark dataset preparation
  -> base diff and optional rule execution
  -> verification passes
  -> generated output descriptor and file
  -> UI result view
```

## Run responsibilities

| Stage | Responsibility |
| --- | --- |
| Setup and access | Persist run setup and resolve user, company, and tenant scope. |
| Source staging | Save uploaded files, text payloads, or configured-source inputs for processing. |
| Base comparison | Normalize records and compute missing-object or matched-pair output. |
| Rule evaluation | Apply RuleSet rules to compare-ready data and matched pairs. |
| Verification | Recheck reported differences against lookup-capable sources before the output is written. |
| Output storage | Store generated output metadata and files for review. |

## Current execution paths

A run starts from one of two entry points. After the trigger, both execute the same stages and the same verification passes.

| Entry point | Where it lives | Starts when |
| --- | --- | --- |
| Interactive saved run | `facade.ReconciliationFacadeServices.run#SavedRunDiff`, implemented in `src/main/groovy/darpan/facade/reconciliation/runSavedRunDiff.groovy` | A user runs a saved run from the app. |
| Automation pipeline | `darpan.reconciliation.automation.AutomationExecutionSupport`, driven by `scan#DueAutomations`, `execute#Automation`, and SFTP polling | A schedule comes due, a user presses **Run now**, or SFTP polling picks up a file. |

The verification decisions live in one place, `darpan.facade.reconciliation.RunVerificationSupport`, so a scheduled run and an interactive run apply the same rechecks. On the automation path, one runtime switch can turn all verification off for an instance.

Separately, a run's compare definition takes one of two shapes:

| Shape | Role |
| --- | --- |
| RuleSet | A saved run points to a `RuleSetCompareScope` with compare sources and optional rules. |
| Mapping | A reconciliation mapping describes source members and comparison behavior. |

Darpan supports both. New run contracts center on `RuleSetCompareScope`; existing services and release history may still reference mappings.

## Keep

Keep decides which records of a side are compared and which are set aside. From Darpan 3.4.0 it runs in Spark after the read, on every run path: interactive runs, automations, retries, replays and the sync pulse. The extractors no longer filter.

`darpan.reconciliation.source.KeepPlanSupport` places each side from its connector row (`SourceSystemConnector`):

| Placement | When | What happens |
| --- | --- | --- |
| `SPARK` | The connector has a `filterParameterName` and no `dataSourceDefinitionId`. | The read gets no filters. Spark runs the connector's built-in Keep lines (`keepLinesJson`), then the tenant's source filters, in that order. |
| `READ` | A data-defined endpoint (`dataSourceDefinitionId` set). | Its filter is a step of its own pipeline, so it still filters at the read. Spark runs nothing. |
| `NONE` | No connector, or no `filterParameterName` (file uploads, databases). | No filters and no Keep. |

An interactive run's source filters are the compare scope's (`RuleSetCompareSourceFilter`), read by `KeepPlanSupport.tenantRuleRows` for one named tenant. An automation runs on its own copy (`ReconciliationAutomationSourceFilter`, taken at create and at `sync#Automation`): `AutomationExecutionSupport.sideKeepOf` reads those rows pinned to the automation's tenant, so a filter edit on the run reaches a scheduled run only through a sync. The key fields and record root are the compare scope's on both paths, as the compare ingests the side.

Built-in Keep lines are data on the connector row, written by the system's own component; core holds no system name. A connector with no built-ins carries `[]`. A built-in line can carry `appliesUnless`, a map of the side's extract options (`extractOptionsJson` on the connector) that switch it off: HotWax orders set exchange orders aside unless the side sets `keepExchangeOrders` (darpan-hotwax 1.3.1), and the orders extract then writes exchange orders it re-reads by key flagged, as the window read does. A `SPARK` side fails, before anything is read, when its connector's `keepLinesJson` is not loaded, and when neither the read nor Spark can filter a side that has Keep rules (no key, or records that are not top-level).

A key field with no path (`orderId`, record root blank) is read as a field of each record of the `records` array when Keep runs in Spark, as the plan gate (`KeepPlanSupport.keyedOnRecords`) reads it (3.4.6); before, the compare failed on it. Uploads, whose records are a top-level array, never keep in Spark.

`darpan.reconciliation.source.KeepStepSupport` splits the side and writes the set-aside artifact beside the extract (`KeepArtifacts`): `<extract>.keep.json` (the summary, one entry per tenant rule with its counts), `<extract>.set-aside.rows` (one row per set-aside record) and, where the connector asks for it (`excludedRecordsSidecar`), the `.excluded.json` side file. The extract keeps every record; every reader of it skips what Keep set aside. The other side is then read by the kept keys only, and the conclude pass reads its set-aside counts from the summary.

A Keep decision saved through moqui-rules (stage `CDS_KEEP_FILE_1` or `CDS_KEEP_FILE_2`) is checked first by `judge.JudgeConfigServices.check#KeepRuleLines`, run as a pre-service ECA on `moqui.rules.RuleServices.store#Rule` (`service/KeepRule.secas.xml`). A line Keep cannot run in Spark (an exists, piece or field-to-field line, an ask, a date or list field, a field of the other side) is refused and nothing is saved.

## Kept copies

A dataset (`darpan.dataset.Dataset`, one tenant, one system and connection) keeps a rolling copy of a source on disk, so a run can be served its window from the copy instead of reading the system live. `DatasetRead` records each refresh. A refresh reads what changed since the last read every day and the whole horizon weekly (`DRK_INCREMENTAL`, `DRK_FULL`), counting records that went missing. The copy keeps only the fields its checks read (`keptFieldsJson`).

`darpan.dataset.KeptCopySupport` decides per side whether the copy covers the run's window, using the copy's own manifest. Served, the slice is written where the live extract would land; not served, the side reads live as before. Refreshes start from `scan_DueDatasets_30m`, seeded paused, and only active datasets are read.

## Peak periods and the sync pulse

A tenant names its busy days as peak periods (`darpan.peak.PeakPeriod`, with run-time moves in `PeakPeriodRunTime`). Settings are resolved at run time by one resolver, `darpan.peak.PeakPeriodSupport`; automations are never rewritten.

- The scheduler holds a run that comes due inside the period's peak hours until they end, and starts a moved run at its set time on its date, in the tenant's zone.
- `darpan.peak.PeakReadPolicy` gives each read the tenant's limits for its local today, cached for 60 seconds: a HotWax share of the normal read rate, and NetSuite reads one at a time (`NetSuiteReadGate`). A failed lookup reads as no limit.
- An extract's page heartbeats touch its automation execution, so a phase slowed by a peak period is not reaped as stuck.

A sync pair (`darpan.pulse.SyncPair`) attaches a light watch to an automation's daily check. `run_SyncPulse` runs every 5 minutes; each due pulse (`darpan.pulse.SyncPulseSupport`) reads the upstream side for a short window, asks the target side by key which of those records it holds, and writes one `SyncPulseSample` (`SPS_OK`, `SPS_FAILED` or `SPS_SKIPPED`). A record missing past the allowance gets one open `SyncPulseOrder`, closed when it arrives or when it leaves the check. A peak period can change a pair's allowance and cadence (`PeakPeriodSync`). The pulse reads through the check's own extractor dispatch and Keep, goes through run admission, and posts to chat only when the past-allowance count moves between zero and not zero. The daily check waits for the allowance before it reads a day.

## Scope modes, flowcharts and lifecycles

A compare scope has a `scopeMode`. Null or `COMPARE` is the two-sided compare above. `EVALUATE` is single-sided: `evaluate#RuleSetCompareScope` reads one source and its rows are the findings, in the missing-diff row shape. The interactive path forks once, early, and `EXTRACT_FILE2` is never opened. An unknown mode, or a FILE_2 source on an `EVALUATE` scope, is refused.

A run flowchart is a `Reconciliation` whose questions form a parent-first tree. Each question is one RuleSet run; the questions under it run on its yes or no branch, and a parent's keys narrow the child's FILE_1 at prepare, so each question answers only for the records that reached it. `run#Reconciliation` and an automation whose `savedRunType` is `reconciliation` walk the tree per window (`darpan.reconciliation.flowchart.RunFlowchartWalker`). A question under one that failed or was switched off ends `AUT_STAT_NOT_RUN`. `import#NetSuiteChecksAsRuns` turns a tenant's NetSuite checks into flowcharts: one START per population, each check a yes question under it. It is safe to repeat, and says why any check was skipped.

A lifecycle is a flowchart compiled by `save#Lifecycle` from a NetSuite account, a start record type, and its stages in order. Every record lands in exactly one named place. Leave-out rules, stage exceptions (`waiveRules`), written findings (`matchRules`) and places marked as not a finding are stored on the lifecycle and recompiled into the tree. A lifecycle walk reads its window once (`darpan.reconciliation.core.RunSnapshotScope`); switch that off with `-Ddarpan.reconciliation.runSnapshot=off`, and every question reads live.

## Conclusions

When a scope has conclusion rules, the `CONCLUDE` stage names every verified finding from a per-run Drools tree (`darpan.reconciliation.conclusion.ConclusionTreeEngine`) and stores the evidence the deciding rule tested. A finding no rule explains is `UNEXPLAINED`. Conclusion catalogues and rules are tenant configuration, loaded per tenant, not seed data.

A condition's operators are evaluated by `ConclusionConditionSupport`, the one evaluator both the walk and the Drools tree call: `IN`, `NOT_IN`, `GT`, `LT`, `GT_ZERO`, `WITHIN_HOURS`, `BLANK`, `NOT_BLANK`, and since 3.4.4 `STARTS_WITH_ANY` and `NOT_STARTS_WITH_ANY` (a prefix from the list, case ignored as `IN` is; a blank value starts with nothing, so `NOT_STARTS_WITH_ANY` holds on it). Keep uses the same two names.

## Audit report morning and progress

`get#AuditReport`, `get#AuditCheckExtracts` and the GraphQL `auditReport` resolve a blank date with `AuditReportGraph.morningOnShow`: yesterday while today's `scheduleTime` in the audit's `scheduleTimeZone` is still ahead, else today. It returns today when the audit's schedule is off, a check of the audit already has an `AuditCheckRun` today, or the requested period had not started yesterday. `retry#AuditCheck` keeps today, because a retry runs now.

`get#AuditProgress` (`AuditSettingsSupport.progress`) answers `asOf`, and on each step `movedDate` (the step's heartbeat date; absent for reads that never heartbeat, such as a Shopify bulk read, a database read or a side waiting its turn) and `expectedRecords`. `expectedRecords` is the same stage's `metricsJson.readCount` on the automation's last successful execution: `RunObservability.endStep` keeps a heartbeated read's last page count there before `recordCount` takes the connector's own count, which can be in other units. A running entry carries the peak period's `limits` from `PeakReadPolicy`.

## Finding acknowledgements, feedback and re-check all

These three let a person act on a finding without touching the morning check's state machine: a finding stays `AUDFS_OPEN` or `AUDFS_FIXED`, and only a check closes it.

**Acknowledgements (3.4.9).** `darpan.audit.AuditFindingAcknowledgement` holds one row per acknowledged finding (`findingId` PK, `companyUserGroupId`, `note`, `acknowledgedByUserId`, `acknowledgedStamp`, `remindDate`, `lastChangedByUserId`, `lastChangedStamp`), in the `DARPAN_ACTIVE_COMPANY_SCOPE` filter. `acknowledge#AuditFinding`, `update#AuditFindingAcknowledgement` and `delete#AuditFindingAcknowledgement` act on a report row, not one finding: `AuditReportAssembler.unitMemberIds` names the order's open lines under the statement and the later-step lines waiting under it, and each gets its own row and its own `AuditFindingEvent` (`AUDFE_ACKNOWLEDGED`, `AUDFE_ACK_CHANGED`, `AUDFE_ACK_REOPENED`, actor `AUDAT_USER`) in one transaction through `audit.AuditLedgerServices`. State is computed on read by `AcknowledgementSupport`: a row is acknowledged while every open finding in it has an acknowledgement made after its last `AUDFE_REOPENED` and today, in the tenant's zone, is before `remindDate` (or `remindDate` is null). A line that breaks later, a passed remind day, or a fix and reopen bring the row back to open. `remindDate` is the acknowledge day plus `audit.acknowledge.remindDays` (default 5). Person events never decide a finding's state in `findingsAsOf`, nor its `lastChecked`. Only the latest morning splits `open` from `acknowledged`; the run update and the digest count acknowledged findings on their own line, and the weekly digest compares open plus acknowledged on both sides. The nightly purge deletes a finding's acknowledgement with it.

**Feedback (3.4.9).** `send#AuditFindingFeedback` (`darpan.audit.FeedbackSupport`) saves a `darpan.audit.AuditFindingFeedback` row (`FB-` ids, tenant-scoped, no FK to the finding) in its own transaction, with the finding's `statementId`, `conclusionCode` (null for an Unexplained finding), `recordKey` and `headline` as snapshots. It then posts a card to `feedback.chat.webhookUrl` (Google Chat or Slack by host; the note is flattened and its chat markup neutralised) and sends the sender `DARPAN_FEEDBACK_RECEIVED`. A failed card or email is logged at `ERROR`, so the error log capture reports it, and never undoes the save. Notes group by tenant, statement and conclusion code; `get#AuditFindingFeedback` and `feedback.recentCount` cover the last `audit.feedback.shownDays` (default 14), and rows are kept past it. A Darpan admin lists them with `admin.FeedbackAdminServices.get#FeedbackList` and answers with `reply#Feedback`, which emails `DARPAN_FEEDBACK_ANSWER` and saves the answer only when the email was sent.

**Re-check all (3.4.9).** `verify#AuditFindings` (`darpan.audit.AuditFindingsVerifySupport`) is `verify#AuditFinding` for every open finding of an audit's period, or of one statement. It groups the open findings by their check's automation and submits one automation run per automation with `auditVerifyKeys` set to all their record keys, so checks that share a saved run share the run. Within one automation, keys are batched on their first key field (`ConclusionKeySupport.firstField`), at most `AuditRecheckSupport.MAX_KEYS` (1,000) first keys a run, so an order's lines ride in one run. Like `verify#AuditFinding` it writes no `AuditCheckRun`: health and the next incremental read are unchanged. Findings whose check has no automation are counted in `skipped`. `get#AuditRecheckProgress` counts the findings whose `lastCheckedStamp` is at or after the returned `checkedSince`, and the closed ones among them. Both are excluded from the CLI allowlist.

## Run stages and observability

A run's progress is recorded so an operator can see where it is, and where it stopped. `darpan.facade.reconciliation.RunObservability` is the single instrumentation point for both entry points.

Each run has one `ReconciliationRunResult` row. Its `statusEnumId` moves from `AUT_STAT_PENDING` or `AUT_STAT_RUNNING` to one terminal status: `AUT_STAT_SUCCESS`, `AUT_STAT_FAILED`, `AUT_STAT_NO_DATA`, `AUT_STAT_SKIP_DUP`, `AUT_STAT_CANCELLED`, or `AUT_STAT_NOT_RUN` (a flowchart question under one that failed or was switched off). The row also carries `currentStage`, a heartbeat date, and `windowTimeZone`, the zone the run window was anchored in.

Each stage writes one `ReconciliationRunStep` row with its own status, timing, and metrics. Stages run in this order (`RunObservability.STAGE_SEQUENCE`):

| Sequence | Stage | Work |
| --- | --- | --- |
| 1 | `RESOLVE` | Load the saved run, its compare scope, and the run window. |
| 2 | `EXTRACT_FILE1` | Extract or stage the first source. |
| 3 | `EXTRACT_FILE2` | Extract or stage the second source. Never opened on a single-sided (`EVALUATE`) scope. |
| 4 | `RECHECK` | Read an audit window's older open findings again by key on each side, and, on a side whose extractor takes `changedSince`, the period's records that changed since the recent read started (3.4.6). Opened only on an audit window that has either. |
| 5 | `COMPARE` | Spark base diff and rule evaluation. |
| 6 | `VERIFY_RETURNS` | Return presence. Free grading, so it runs before any paid lookup. |
| 7 | `VERIFY_MISSING` | Missing-diff recheck. |
| 8 | `VERIFY_EXCHANGE` | Exchange presence. |
| 9 | `CONCLUDE` | Name every verified finding by the scope's conclusion rules. Opened only when the scope has rules. |
| 10 | `WRITE_OUTPUT` | Write the verified result artifact and the run-result summary. |
| 11 | `NOTIFY` | Send run-completion alerts. |

darpan-ui's `RUN_STAGE_SEQUENCE` holds the same order by position; change both together. Rows written before 3.4.4 number `VERIFY_MISSING` 6, `VERIFY_EXCHANGE` 7 and `VERIFY_RETURNS` 8, and rows written before `RECHECK` existed number `COMPARE` through `NOTIFY` one lower.

Verification runs before `WRITE_OUTPUT`, so the file a user downloads is the corrected one. Lookup and brain answers are captured into the run folder, so a replay answers them without calling any system; a capture never changes a conclusion. Each pass has its own stage code and records the systems it rechecked in its own step metrics. A pass that declines to run records why.

Rows written before 2.0.0 carry a single `VERIFY` code at 5, with `WRITE_OUTPUT` and `NOTIFY` at 6 and 7. New runs never enter `VERIFY`. A consumer that reads `stageCode` or `stageSequence` must accept every set.

| Pass | What it rechecks |
| --- | --- |
| Return presence | Runs first, free. For returns runs between Shopify and HotWax OMS, regrades return and refund events reported missing on one side. An event younger than the sync grace period is pending, not missing. An event before the run window, a refund on a cancelled order, or an unrefunded Shopify return draft on an order that already has a booked OMS return is not reported as a gap. |
| Missing-diff recheck | Rows reported missing on a side whose connector supports point lookups are looked up again in that system. Rows the lookup confirms present are removed and the counts adjusted, with an audit note. A failed or skipped lookup changes nothing. A side is looked up only when it is keyed on the id kind its connector's lookup answers (`lookupIdField`). When its missing rows are more than `lookupMaxShare` percent (default 5) of the records checked against it, an audit window (`window.auditReportDate` set, passed down as `auditRun`) looks nothing up and warns (`sideOutcomes` `skipped: OVER_SHARE`); any other run looks every row up and adds a note that the read or the pairing needs fixing (`overShare: true`). `RunPathParityGateTest` keeps the gate to audit windows. |
| Exchange presence | For order runs between Shopify and HotWax OMS, checks that each Shopify exchange in the window was imported into OMS. Only lookup-confirmed absences become rows. |

## Stuck-run recovery

If a JVM crash or container restart kills a run mid-flight, its run-result row can be left in a running state forever, which blocks re-triggering. An internal scheduled reaper handles this:

```text
reconciliation.ReconciliationAutomationServices.sweep#StuckReconciliationRuns
```

It flips `ReconciliationRunResult` and `ReconciliationAutomationExecution` rows still in running or pending state, whose last update is older than the `darpan.reconciliation.runHealth.reaperStaleMinutes` setting (a Darpan operator edits it in the admin app), to failed with an explanatory status message. The service is internal only (`allow-remote="false"`) and is not part of the JSON-RPC surface.

The reaper runs as the `sweep_StuckReconciliationRuns_10m` service job. A job run killed mid-job leaves its `ServiceJobRunLock` row behind, and the job does not run again until the lock expires. Every job Darpan ships sets `expireLockTime` to 360 minutes (Moqui's default is 1440), so a killed task stalls the reaper and the automation scan for at most 6 hours.

## RuleSet compare flow

The RuleSet path is built from these records:

- `RuleSet`
- `RuleSetCompareScope`
- `RuleSetCompareSource`
- `Rule`
- `ReconciliationRun`
- Generated output descriptor records

The compare flow is:

1. The facade service creates or loads a saved run and its compare scope.
2. Generic reconciliation saves uploaded or text payloads in a tenant-scoped temp location.
3. `prepare#RuleSetCompareScope` resolves compare sources and builds normalized Spark datasets.
4. `reconcile#RuleSetCompareScopeBaseDiff` finds base missing-object differences and matched pairs.
5. `reconcile#RuleSetCompareScope` preserves base diffs and appends rule-generated diffs from matched pairs.
6. The backend writes result data and summary metadata as a generated output.

### Read fields

An extractor that declares `readFields` reads only the fields its run needs. An automation's read sends it the fields the side's rules and Keep read, plus any the source's own `parameters.readFields` asks for: the source's first, then the rules', each once (`AutomationExecutionSupport.withAskedReadFields`, 3.4.7). Before 3.4.7 the rules' list replaced the source's. A service that does not declare `readFields` gets neither.

### Order lines for audit findings

From 3.4.7 an audit finding's order record can carry its lines, so the audit page lists them by SKU with each system's status. From 3.4.8 each side turns it on with a read option its connector declares in `extractOptionsJson`, as HotWax `keepExchangeOrders` is. The run editor offers it in the side's options card when a run is created, and from 3.4.10 the run's **Ruleset Manager** lists each declared option under **Read options**, with a switch that saves the run at once through `save#RuleSetRun` (`file1ExtractOptions` / `file2ExtractOptions`); the choice is stored in the side's `RuleSetCompareSource.extractParametersJson`, read by the manual run, and copied into the automation source's parameters on sync. Off is the default and is never stored. A side with either option on keys its own dataset options, so it reads live rather than from a kept copy.

- HotWax orders (darpan-hotwax 1.3.4): option `withOrderItems`, label "Order items", on `OMS_GQL`. `extract#HotWaxOmsGqlOrders` takes it (Boolean, default false), and `OmsExtractSupport.readFieldsWithOptions` then adds `orderItems` to the fields read. The derived field `orderItems` is read by order id once per page, as `itemQuantity` is, each item with `orderItemSeqId`, `externalId` (the Shopify line id), `productId`, `sku`, `quantity` and `statusId`. A read that asks for it is not covered by the shared orders read (`OmsGqlQueries.sharedOrdersCover`), so the check reads its own window plus one item call per page.
- Shopify orders (shopify-darpan 0.11.2): option `withLineItems`, label "Order lines", declared on the `SHOPIFY` connector from darpan 3.4.8; `extract#ShopifyOrders` has taken it since 0.11.2. The read uses the extract-only source `SHOPIFY_ORDERS_WITH_LINES`, which selects each order's `lineItems` (id, SKU, name, quantity, current and unfulfilled quantity) in the same bulk query; `listSources` never lists it. `ShopifyOrderLinesNesting` puts each line back under its order. The request metadata reports `withLineItems` and `orphanLines`: above 0, that many lines arrived away from their order and were left off, and the read adds a warning.

`AuditReportAssembler.recordFacts` turns either into the record's `lines`, each `{id, sku, name, quantity, status}`. A HotWax item's `id` is its `externalId`, so a Shopify line and its HotWax item share one id and the app shows them as one row. A Shopify line's `status` comes from its quantities: `Removed`, `Fulfilled`, `Unfulfilled`, or "1 of 3 unfulfilled". A HotWax item's is its status in words.

## Run-completion notifications

Runs that reach a terminal state alert the owning tenant so sync issues surface without anyone watching the run history page. Destinations are resolved per run rather than per tenant, which is what lets one person follow a single run without changing shared configuration.

1. A run reaches a terminal state through one of three paths: a manual saved-run diff (`facade.ReconciliationFacadeServices.run#SavedRunDiff`), a scheduled automation execution, or SFTP polling. Terminal states are `AUT_STAT_SUCCESS`, `AUT_STAT_FAILED`, `AUT_STAT_NO_DATA`, `AUT_STAT_SKIP_DUP`, and `AUT_STAT_CANCELLED`.
2. The completion path calls `darpan.reconciliation.notification.TenantNotificationSupport`, which resolves destinations through `resolveDestinationChatSpaces`: the automation's linked `chatSpaceId`, plus the snapshotted space on every `darpan.reconciliation.ReconciliationRunNotifySubscription` row for the run.
3. That set is deduplicated and filtered to `darpan.reconciliation.TenantChatSpace` rows that are active, can deliver, and belong to the run's own tenant. A dropped *automation-linked* space is logged as a warning; a dropped subscriber space is expected churn and stays silent.
4. The helper builds the message through `reconciliation.ReconciliationNotificationServices.build#RunCompletedPayload` and posts it to each surviving destination.

Delivery is claim-then-deliver: a single claim per run-result means at most one notification pass even when several stages report completion. A failed delivery still consumes the claim; there is no automatic redelivery. Subscription rows are purged once the run is terminal. The payload includes the run name, tenant label, result ID, a link back to the run result, the difference count, and the only-in-source counts. The run-result link base URL comes from the `DARPAN_APP_BASE_URL` environment variable or the `darpan.app.baseUrl` property, falling back to the first allowed origin.

Automation executions have one more end state. An execution that fails with a transient error is retried; one that exhausts its retries ends in `AUT_STAT_DEAD_LETTER`. `facade.ReconciliationFacadeServices.reprocess#AutomationExecution` resets a failed or dead-lettered execution to pending with a fresh retry budget.

### Run errors

From 3.4.6 an automation run's error never reaches a tenant's destination. `darpan.ops.RunErrorKinds` names an execution's error from its terminal row: `FAILED`, `DEAD_LETTER` (after the last retry only), or a `AUT_STAT_NO_DATA` close whose `noDataKind` is `ONE_SIDE_EMPTY` (one side read nothing, the other read records) or `KEPT_NOTHING` (Keep kept none of a side's records). A rule that fails to build or evaluate ends `FAILED` with the rule's error on the row. Both sides empty is a quiet day and no error. The stuck-run reaper's failures take the same path. `AutomationExecutionSupport.notifyRunError` then:

1. Posts one card to Darpan's own chat space (`errors.chat.webhookUrl`; Google Chat or Slack by host) per audit check the automation runs, or one for an automation with no check. `darpan.ops.RunErrorNotice` (tenant, check or automation, run day in the automation's zone, trigger) is the dedupe key, so a second failure that day posts nothing; scheduled failures count a streak, and a `manual` or `play` run has its own slot.
2. Sends the tenant only the copy block `DARPAN_ERROR_NOTICE` / `client.notrun` ("*name* did not run this morning. Darpan has been alerted and is working on a fix."): to every notify-me subscriber on any trigger, and to the automation's chat space for a scheduled run of an automation that feeds no audit, once per automation per run day. An audit's tenant line is its run update, which says which checks did not run or partly ran.

An audit check on such a window records not run with the side's reason and closes nothing. Each execution keeps `file1ReadCount` and `file2ReadCount` (what the read returned) beside the kept counts, `noDataKind`, and `triggerType` (`scheduled`, `manual` or `play`; blank on older rows, read as scheduled). `run#SavedRunDiff`, a saved run started from the app, takes the same path from 3.4.7 when it throws or its rules do not fully evaluate (`AutomationExecutionSupport.notifySavedRunCompleted`, then `notifySavedRunError`). Darpan's error space gets one `FAILED` card with trigger `manual` and the saved run's name, deduped per day on `savedRun:<savedRunId>` in the tenant's zone. Its notify-me subscribers get only the copy block `DARPAN_ERROR_NOTICE` / `client.runfailed` ("*name* did not finish. Darpan has been alerted and is working on a fix."), never the error or the rule warnings. A run whose cancel was requested while its rules failed ends `CANCELLED`: no card, no line, and its subscriptions are purged.

`darpan.ops.ErrorLogCapture` (a Moqui tool factory, `ErrorLogToolFactory`) keeps the instance's `ERROR` log lines in memory, grouped by fingerprint (logger plus message with numbers and ids masked, at most 500 a window), and `flush_ErrorLog_5m` stores them in `ErrorLogEntry`, one row per fingerprint per UTC day, purging rows older than 30 days. `send_ErrorDigest_hourly` sends the daily Darpan error email (`DARPAN_ERROR_DIGEST`) to `errors.email.to` at `errors.digest.hourUtc`, once a day even when nothing happened, claimed per UTC day in `ErrorDigestSend`: the run errors since the last email, the watchdog (an audit check with no successful scheduled run for `errors.watchdog.hours`, an active statement's check with no automation, `errors.emptyStreak.days` scheduled runs in a row that read nothing), and the log errors. A one-line summary posts to `errors.chat.webhookUrl`, and says so when no email went. With neither setting there is nothing to send.

After an audit run with Unexplained findings, `AuditRunUpdateSupport` emails `audit.unexplained.email.to` a CSV of them (copy blocks `subject.unexplained`, `unexplained.*` of `DARPAN_AUDIT_RUN`), once per run, even when the audit's run update is off. These three addresses are Darpan settings, never a tenant's.

### Chat providers

A chat space posts to one provider, recorded in `chatProviderEnumId`:

| Provider | Enum | Delivery |
| --- | --- | --- |
| Google Chat | `CHAT_PROV_GOOGLE` | Incoming webhook. A null provider reads as Google Chat, because rows written before Slack support have no provider. |
| Slack | `CHAT_PROV_SLACK` | The bot token of a connected Slack workspace (`chat.postMessage` to `slackChannelId`) when the space names a workspace install, or an incoming webhook otherwise. |

The webhook URL is validated on save:

- Google Chat: `https` on `chat.googleapis.com`, a `/v1/spaces/…/messages` path, and `key` and `token` query parameters.
- Slack: `https` on `hooks.slack.com`, a complete `/services/…` path.

Webhook URLs are stored in clear text in `TenantChatSpace.webhookUrl`, and `list#TenantChatSpaces` returns them to members of the tenant. Treat read access to a tenant's settings as access to its webhook URLs. Slack bot tokens belong to the workspace install and are not returned.

The registry, the per-user default, and Slack setup are configured through:

```text
facade.SettingsFacadeServices.list#TenantChatSpaces
facade.SettingsFacadeServices.save#TenantChatSpace
facade.SettingsFacadeServices.delete#TenantChatSpace
facade.SettingsFacadeServices.get#UserNotificationDefault
facade.SettingsFacadeServices.save#UserNotificationDefault
facade.ReconciliationFacadeServices.subscribe#RunNotification
facade.ReconciliationFacadeServices.unsubscribe#RunNotification
facade.SlackFacadeServices.begin#SlackInstall
facade.SlackFacadeServices.save#SlackBotToken
facade.SlackFacadeServices.get#SlackInstall
facade.SlackFacadeServices.list#SlackChannels
facade.SlackFacadeServices.disconnect#SlackWorkspace
```

`save#TenantChatSpace` requires tenant write access; `save#UserNotificationDefault` and the subscribe pair are personal preferences and do not. `delete#TenantChatSpace` hard-deletes only unreferenced spaces — a space an automation or subscription points at must be deactivated instead. A Slack space can only name a workspace install that belongs to the same tenant.

The single-webhook `darpan.reconciliation.TenantNotificationSetting` entity this replaced is retired. `reconciliation.ReconciliationNotificationServices.migrate#TenantNotificationSettings` is the one-time upgrade that copies each tenant's old webhook into a space named `Default space` and links that tenant's space-less automations to it. It is idempotent, internal only (`allow-remote="false"`), and registered as a [data migration](/backend/migrations). The product-side setup flow is described in [Manage tenant settings](https://docs.drpn.ai/guides/manage-tenant-settings).
