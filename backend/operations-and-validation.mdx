These checks confirm engine changes before merge; run them from the Moqui framework checkout that contains the Darpan component unless a command states otherwise. Start with focused tests, then widen.

```text
<moqui-framework>
```

## Common checks

Run the narrowest check that covers your change first, then widen.

| Check | Command |
| --- | --- |
| Run only the tests your diff can break | `runtime/component/darpan/scripts/focused-test.sh [base-ref]` |
| Run one backend test class | `./gradlew :runtime:component:darpan:test --tests <TestClass>` |
| Run the classes that do not boot Moqui (fast) | `./gradlew :runtime:component:darpan:unitTest` |
| Run the classes that boot Moqui | `./gradlew :runtime:component:darpan:smokeTest` |
| Run the full suite as the two pools above | `./gradlew :runtime:component:darpan:testAll` |
| Run the full suite, one JVM per class | `./gradlew :runtime:component:darpan:test` |
| Run the MySQL-only tests (needs a local `darpan_test` MySQL database) | `./gradlew :runtime:component:darpan:mysqlTest` |
| Compile the Darpan backend component | `./gradlew :runtime:component:darpan:compileGroovy` |
| Check the committed API contract against the service XML | `./gradlew :runtime:component:darpan:checkApiContract` |
| Validate component organization rules | `./gradlew :runtime:component:darpan:verifyOrganization` |
| Build the component jar | `./gradlew :runtime:component:darpan:jar` |
| Load seed and upgrade data | `./gradlew :runtime:component:darpan:loadDarpanUpgradeData` |

`focused-test.sh` picks test classes from the files changed since the base ref (default `origin/main`) and falls back to the full suite for anything it cannot map. Pass `-n` as the second argument to print the selection without running it. It is a faster inner loop, not a substitute for the full suite before you push.

Tests tagged `mysql` cover InnoDB locking behaviour that the default H2 test database cannot reproduce. They are excluded from `test`, `unitTest`, and `smokeTest`.

## Runtime baseline

| Piece | Version or setting |
| --- | --- |
| JDK | 21 (the component's Gradle toolchain) |
| Framework | Moqui 4, built from the `drpn-ai/moqui-framework` fork, with embedded Bitronix as the JTA transaction manager. Darpan 3.1.0 needs the fork's `master` with PBKDF2 password hashing and the password-only sign-in closures. |
| Build | Gradle 9 |
| Comparison | Apache Spark SQL 4.2.1 (Scala 2.13, ANSI mode on); every embedded `SparkSession` sets `spark.ui.enabled=false` |
| Rules | Drools 10.2.0 (`drools-engine`, `drools-mvel`, `drools-xml-support`, `kie-api`), with MVEL 2.5.2.Final |
| Passkeys | webauthn4j-core 0.30.3 (with jackson-dataformat-cbor), Apache-2.0 |
| MySQL driver | Connector/J 9.7.0; deployments use the `mysql8` database configuration |
| PostgreSQL driver | 42.7.7 |

Spark on JDK 21 needs a set of `--add-opens` JVM flags, plus `-Dio.netty.tryReflectionSetAccessible=true`, `-XX:+EnableDynamicAgentLoading` and `--enable-native-access=ALL-UNNAMED`. The component's test tasks pass them, and the production entrypoint exports them through `JAVA_TOOL_OPTIONS`. A local server needs the same flags; without them a compare fails at runtime. Spark 4 and Drools 10 share ANTLR 4.13, so do not pin ANTLR to make them agree.

Production images are built from a separate, private deployment repository (`darpan-docker-config`). Its production entrypoint refuses to start unless the database connection (`Moqui_DB_HOST`, `Moqui_DB_USER`, `Moqui_DB_PASSWORD`, `Moqui_DB_NAME`), `entity_ds_crypt_pass`, and `JWT_KEY` are set. `entity_ds_crypt_pass_old` is optional and used only during a key rotation.

## Sign-in and session settings

The component's `MoquiConf.xml` sets these for every deployment:

| Setting | Value |
| --- | --- |
| Web sign-in | Ends after 60 idle minutes (`session-config timeout="60"`, and the login key slides 60 minutes on with each request), and at most 24 hours after sign-in (`login-key expire-hours="24"`). `AuthSessionSupport.enforceWebSignInLifetime` signs out an expired one before the request runs. |
| CLI sign-in | Lasts 7 days (`CliAccess.SIGN_IN_DAYS`). Revoking the sign-in, or disabling the user, ends it on the next call. A darpan-admin sign-in (`scope` `ADMIN`) is approved in the browser by a super admin with two-factor on, using the code the terminal shows, and lasts 12 hours; only that session may call `admin.*` from a CLI. |
| Signed out everywhere | A key issued before the user's `UserAccount.sessionsEndedDate` is refused. |
| Passwords | At least 12 characters (`password min-length="12"`). The framework hashes new and changed passwords with PBKDF2-HMAC-SHA256 and re-hashes an older hash at the next sign-in. |
| Password-only sign-in | Refused. `PasswordOnlyRouteFence` runs first in the webroot before-request hook: a request carrying an HTTP Basic `Authorization` header, or `authUsername`, `authPassword` or `authUserAccount` anywhere in its parameters or JSON body, is signed out and answered 401. The framework's `/Login`, `/SecondFactor` and `/ChangePassword` screens answer 404. Clients sign in through `facade.AuthFacadeServices.login#Session`, or use a GraphQL API key. |

Two-factor sign-in is configured per role in `darpan.auth.TwoFactorRolePolicy` for `ADMIN`, `DARPAN_SUPER_ADMIN`, `DARPAN_ADMIN` and `DARPAN_TENANT_ADMIN`. The role `EVERYONE` covers every person with a tenant membership or a Darpan role, and dating it, or `ADMIN` or `DARPAN_SUPER_ADMIN`, needs the setter to keep a second way back in (a passkey and an authenticator app, or unused recovery codes); clearing a date is never blocked. Every role starts optional; `admin.SecurityAdminServices.update#TwoFactorPolicy` makes a role required from a date, read on the UTC calendar. From the date, a person with no app or passkey is taken into setup at sign-in instead of being locked out. `send_TwoFactorReminders_daily` (15:00 UTC, scheduler node) emails people a dated policy covers who have not enrolled, at most one a day. Authenticator-app secrets are stored encrypted (`TwoFactorFactor`), recovery codes as salted SHA-256 hashes, and passkeys as webauthn4j attested credential data.

## Scheduled data cleanup

| Job | Schedule | What it does |
| --- | --- | --- |
| `purge_ReconciliationGeneratedFiles_daily` | 02:00 daily | Deletes generated result files older than `darpan.purge.generatedOutput.days` (default 15). |
| `purge_ReconciliationExtractFiles_daily` | 02:15 daily | Deletes raw source extract files `darpan.purge.extract.days` after their run (default 7; `reconciliation.ReconciliationGenericServices.purge#ExtractFiles`). Result files and findings are not touched. |
| `run_DataRetention_daily` | 03:30 daily, seeded paused | Deletes audit findings, run results, AI transcripts and agent query logs older than their retention period (`retention.RetentionServices.run#Retention`), tenant by tenant in batches of `darpan.retention.batchSize` (default 500), each batch in its own transaction. |

Retention periods are settings, not JVM properties: `darpan.retention.auditFinding.days`, `darpan.retention.runResult.days`, `darpan.retention.agentMessage.days` and `darpan.retention.agentQueryLog.days`. Edit them on the admin app's Schedule page (Retention section) or with `darpan-admin retention`. An unset period keeps that table forever, so resuming the paused job deletes nothing until a period is set. A tenant can override a period with a number of days, `forever` or `inherit`. Shortening a period while `run_DataRetention_daily` is running, and resuming the job, each need a preview first; `admin.RetentionAdminServices.dryRun#Retention` counts what a run would delete, per table and tenant, and can preview periods that are not set yet.

The two purge periods are plain settings, edited from the same Schedule page or with `darpan-admin settings`; they need no preview. A `-D` system property with the same name is only a fallback: a setting row wins over it, and it wins over the default.

A job's cron, pause state and parameters are edited on the Schedule page too (or with `darpan-admin job`). Those edits survive deploys; an edit made in Moqui Tools is reverted by the next seed load.

## When to run broader checks

Run broader backend checks when a change touches:

- Shared facade services
- Entity definitions or seed data
- Active tenant or permission behavior
- Reconciliation run execution
- Generated output descriptors or file locations
- RuleSet compilation or execution
- JSON schema validation or inference

## Backend service review checklist

Backend engine changes are ready to merge when:

- The owning XML service contract is clear.
- Inputs and outputs are documented in the service definition.
- Access checks run before scoped data is returned or mutated.
- Entity queries include active tenant or company filters where required.
- Groovy helpers do not hide normal service orchestration.
- Generated outputs include both descriptor metadata and scoped file handling.
- Tests cover the changed contract or processing path.

## Expected service documentation

Backend service documentation includes:

- Service name
- Owning file
- Inputs and outputs
- Authentication and authorization expectations
- Runtime side effects
- Verification path

## Troubleshooting

For backend failures, read the earliest meaningful backend log entry for the request. The final exception often hides the first contract or data-shape problem.
